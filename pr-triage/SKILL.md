# pr-triage

## 필요한 것 — `red-team` 은 필수 의존이다

이 스킬은 `red-team` **위에서** 돈다. 선택 사항이 아니다.

| 무엇 | 왜 |
|---|---|
| `red-team` 스킬 설치 | 트리아지 상태(`pr-<N>-triage.json`)와 의사결정 기록이 같은 `~/.red-team/runs2/<repo>/<branch>/` 를 쓴다. 경로 규칙을 복제하면 두 스킬이 다른 디렉토리를 가리키고 "이미 처리한 코멘트" 가 조용히 사라진다 |
| `red-team` 0단계(리뷰 엔진) 완료 | 6절 코드 게이트가 `run_round.py` 를 부른다. 엔진 미설정이면 첫 라운드가 그 자리에서 종료된다 |
| `gh` CLI 인증 | 코멘트 수집·회신이 전부 `gh api` 다 |
| code-hub MCP (선택) | 레포 밖 계약 주장(BE 응답 형태·에러 코드) 확인에 쓴다 — 2절. 없어도 동작하며, 그 경우 해당 코멘트는 사용자에게 올라간다 |

이 스킬만 받았다면 `red-team` 도 같이 설치한다 — 같은 저장소에 형제로 들어 있다.
**전역·프로젝트 로컬 어느 쪽이어도 되지만 둘을 같은 위치에 둔다** — 스크립트가 형제 디렉토리를
먼저 찾고, 그다음 `~/.claude/skills/`, `<cwd>/.claude/skills/` 를 본다. 못 찾으면 상태 저장
경로를 정할 수 없으므로 찾아본 경로를 전부 보여주며 그 자리에서 멈춘다.

## 왜 이 스킬이 있나

PR 을 올리면 리뷰가 붙고, 그때부터 같은 일이 반복된다 — 코멘트를 읽고, 이게 이미 검토한 것인지
새 결함인지 판단하고, 응답을 쓰고, 고칠 것은 고친다. 매번 사람이 지시해야 하고 매번 처음부터
생각해야 한다.

반복되는 부분은 셋이다. ① 코멘트를 세 엔드포인트에서 긁어모으고 누가 리뷰어인지 가리기
② 리뷰가 **어느 커밋을 보고 쓴 것인지** 확인하기 ③ 응답 형식 맞추기. 이건 기계가 할 일이다.

판단 자체는 여전히 사람·모델이 하지만, `red-team` 게이트를 거친 티켓이면 근거가 이미 디스크에
있다 — `~/.red-team/runs2/<repo>/<branch>/<라운드>/` 에 변경 의도·불변식·기각한 대안·스코프 경계·
이미 반영한 지적·철회한 주장이 남아 있다.

**다만 기록 대조가 주된 일이 아니다.** 과거 PR 30개를 세어보니 응답의 82.7%가 "지적이 맞습니다"였다
(2절). 기록은 **"이 티켓에서 고칠 것인가"** 를 판단하는 근거이고, 사실 판단을 대신하지 않는다.

## 흐름

```
        ┌─ 감시(Monitor) ── 신규 코멘트 없으면 아무 일도 하지 않는다
        ↓
신규 코멘트 → ① 사실인가(코드) → ② 이 티켓 범위인가(기록) → 분류
        ↓
    ⚠ 분류 확인 (라운드당 1회) ── 스코프 밖 목록과 나란히 보여주고 승인받는다
        ↓
    real-defect → 수정 → 검증(tsc·lint·test) → red-team 코드 게이트 → GO
        ↓
    decisions.md 기록(6-1) → 회신 초안 → ⚠ 게시 승인 → 게시 → 커서 갱신 ─┘
        ↓ approve·LGTM 코멘트 관측 → 사용자에게 본문 최신화 안내
    (사용자 지시 시) PR 본문 초안 → ⚠ 승인 → 신규 코멘트 재수집 → 게시 (9절)
```

**사람 게이트가 둘이다: 분류 확인과 게시 승인.** 둘 사이(수정·검증·게이트)는 사람 없이 간다.
PR 이 approve·LGTM 을 받으면 본문 최신화를 안내하고, 사용자가 실행하라고 할 때 초안
승인을 받아 갱신한다(9절) — 라운드 안의 게이트가 아니라 사람이 여는 마무리 단계다.

분류 확인을 넣은 근거는 실측이다. 블라인드 30문항(2회)에서 **"미룰 것을 고칠 것으로 본" 오류가
두 번 모두 30%** 였다. 수정이 자동이면 이 오류가 곧 **범위 밖 결함까지 고쳐 PR 을 비대하게
만드는 것**이 된다. 2절에 두 질문 분리를 써넣은 뒤에도 수치가 안 내려갔다 —
**문서로 절차를 적는 것만으로는 그 절차를 따르지 않는다**는 것이 이 수치의 뜻이다.

기계적 대조로 막는 안을 검토하고 기각했다. `## 스코프 밖` 은 자유 서술 산문이고 리뷰 코멘트도
산문이라, 둘을 맞춰보는 것 자체가 지금 30% 틀리는 그 판단이다. 스크립트는 **목록을 정확히
출력할 수 있을 뿐 대조를 대신할 수 없다.** 게다가 만들어도 개선을 검증할 표본이 없다
(깨끗한 쌍 23개, 드문 라벨 0~2건). 그래서 오차를 없애는 대신 **사람이 30초에 걸러내는 위치로
옮겼다.** 라운드당 한 번이고, 반복 지시를 없애려는 목적과 충돌하지 않는다 —
지시는 사라지고 확인만 남는다.

### 0. 감시 걸기 — loop 는 이 스킬이 만들지 않는다

PR 을 올린 직후 `Monitor` 도구에 감시기를 물린다. 신규 코멘트가 올라올 때만 알림이 오므로
**아무 일 없는 동안 모델이 깨지 않는다** — `/loop <간격>` 으로 주기 실행하는 것보다 싸다.

```
Monitor(command: "python3 ~/.claude/skills/pr-triage/scripts/watch_comments.py --pr <N>",
        description: "PR #<N> 신규 리뷰 코멘트", persistent: true)
```

첫 실행은 **기존 코멘트를 알리지 않는다**(알림 폭주 방지). 이미 쌓인 미처리분은 아래 1절로 한 번에 본다.
신규가 24시간 없으면 스스로 종료한다(`--max-empty-hours`).

세션을 오래 띄워두지 못하는 상황이면 `--once` 로 한 번만 확인하게 하고 `/loop 10m` 에 태워도 된다 —
대신 신규가 없어도 매번 모델이 깨므로 Monitor 쪽이 싸다.

알림이 오면 1절부터 진행한다. 알림 하나가 곧 라운드 하나다.

### 1. 수집

```bash
python3 ~/.claude/skills/pr-triage/scripts/fetch_comments.py --pr <N> --new-only
```

`--new-only` 는 **아직 처리하지 않은** 리뷰 코멘트만 보여준다(커서 기준). PR 번호·저장소를
생략하면 현재 브랜치에서 찾는다. JSON 이 필요하면 `--out <경로>`.

커서는 `~/.red-team/runs2/<repo>/<branch>/pr-<N>-triage.json` 에 있고 두 목록으로 나뉜다 —
`notified`(감시가 알린 것, 중복 알림만 막는다)와 `triaged`(승인·게시까지 끝난 것).
**둘을 나눈 이유**: 알림 직후 세션이 죽어도 처리 대상이 사라지면 안 된다.

출력은 시간순 목록이고 표시가 둘 있다.

- `→` — **내 마지막 응답 이후의 리뷰 코멘트**(확실한 미응답). 그 앞쪽도 부분적으로만 답했을 수
  있으니 본문을 읽고 판정한다. 봇이 번호 매긴 여러 지적 중 일부만 남는 경우가 흔하다
- `+Nc` — **그 코멘트 이후 푸시된 커밋 수.** 크면 리뷰가 낡은 코드를 봤을 수 있다.
  실측에서 "이미 반영됐다" 응답의 주된 원인이 이것이었다(30개 PR·133응답 중 19건).
  N 이 크면 **해당 커밋들을 먼저 확인한다** — 이미 고쳐진 것을 다시 분석하는 낭비를 막는다
- `↻N` — **봇 fingerprint(`<!-- hermes:fp=… -->` 마커) 기준 그 지적의 게시 회차.**
  **재게시 회차는 `fp_seq` 가 유일한 진실이다 — 봇 산문의 "N번째"나 기억으로 세지 않는다**
  (#9588 실물: 산문은 "3번째"라는데 fp 기준 2번째였다). 마커 2개짜리 코멘트는 fp 별로
  따로 센다(fps 는 리스트다). 회차가 2 이상이면 7절의 봇 리뷰어 분기를 따른다
- `∉diff` / `∉hunk` — **inline 코멘트의 위치가 변경 파일 목록/new-side hunk 밖.** 낡은
  커밋·범위 밖을 가리키는 신호다. 판정이 안 되는 경우(outdated 라 line 이 null, side=LEFT,
  patch 없는 바이너리·대형 diff, 변경 파일이 API 상한 3000 근접)는 null 로 두고 표시하지
  않는다. **표시일 뿐 걸러내지 않는다** — 범위 밖 지적도 사실관계는 유효할 수 있다
  (#1003 의 Noah 문서 결함이 그랬다)

**diff 플래그의 한계를 알고 쓴다.** 플래그는 inline 코멘트에만 계산된다 — 봇이 전부
top-level(issue) 코멘트로 게시하는 레포(#1003 이 그랬다)에서는 기계 플래그 적용이 0건이다.
그런 코멘트의 범위 대조는 `--show-files` 가 출력하는 변경 파일 목록과 본문 속 경로를 모델이
대조한다(실물 검증: #1003 봇 헤더의 repo-상대경로는 변경 파일 목록과 문자열 완전 일치 —
목록 멤버십 대조가 된다). 목록까지 기계, 대조는 모델+사람 — `--show-scope` 와 같은 역할 분담이다.

**작성자 계정으로 올라오는 리뷰가 있다.** 사내 리뷰 봇이 그런 경우가 있다 — 그래서 작성자만으로는
리뷰와 내 응답이 갈리지 않고, 스크립트는 `🤖` 마커로 가른다(`--bot-marker` 로 바꿀 수 있다).
**fp 마커는 🤖 보다 강한 봇 서명이다** — hermes 는 사람 리뷰어 계정으로 🤖 없이 재게시하는
실물이 있어(#9588), 비-blockquote 라인에 fp 마커가 있으면 스크립트가 봇으로 판정한다.
`<APPROVED>` 로 표시된 리뷰는 보통 응답 대상이 아니지만, 본문에 실질 지적이 담긴 승인도 있으니
본문을 확인한다.

### 2. 두 질문을 따로 묻는다 — "맞나"와 "여기서 고칠 것인가"

과거 PR 30개(리뷰 570건·응답 133건)를 세어보니 **응답의 82.7%가 "지적이 맞습니다"** 였다.
그래서 **사실 판단의 기본값은 "리뷰어가 맞다"** 다. 반박을 찾는 쪽으로 무게를 두면 방향이 틀린다.

**그런데 이것이 범위 판단까지 덮으면 안 된다.** 지적이 사실이어도 이 티켓에서 고칠 것이
아닐 수 있다. 블라인드 20문항으로 재보니 **미룰 것을 고칠 것으로 본 오류가 6건(30%)** 이었고,
전부 "맞는 지적이니 고친다"로 직행한 결과였다. 수정이 자동인 loop 에서 이 오류는
**범위 밖 결함까지 고쳐 PR 을 비대하게 만든다**(스코프 크립).

그래서 코멘트마다 **두 질문을 순서대로** 묻는다.

1. **사실인가?** — 코드로 확인한다. 기본값은 "맞다"
2. **이 티켓에서 고칠 것인가?** — `context.md` 의 `## 스코프 밖`·후속 티켓 목록과 대조한다.
   사실이어도 범위 밖이면 `out-of-scope` 다

두 질문의 답이 독립이라는 것이 요점이다. 실측에서 **정답 라벨이 `["out-of-scope","real-defect"]`
처럼 겹치는 경우가 흔했다** — "맞는 지적이고, 다만 이 PR 에서는 안 고친다"가 정상적인 판정이다.

3·4절의 기록 대조는 두 번째 질문의 근거이고, 1번을 대신하지 않는다.

#### diff 가 문서뿐이면 — 기본값 적용 전에 대조를 먼저 통과시킨다

82.7% 는 **코드 PR** 실측이다. diff 가 문서뿐이면(docs-only) 실측 유효율이 ~28% 로
역전된다(product-hub#1003, 94건 중 무효 72% — 자기참조 38.3%·범위 밖 21.3%). 기본값
자체를 "리뷰어가 틀렸다"로 뒤집지는 말되, **`--show-files` 변경 파일 목록과의 대조
(범위 밖·유령 라인)와 아래 미결 등재 대조를 먼저 통과시키고** 남는 것에만 기본값을
적용한다. (스크립트의 diff 플래그는 inline 한정이라 top-level 봇 코멘트에는 적용 0건 —
이 대조는 모델이 한다.)

#### 지적 대상이 PR diff 안 문서의 미결 표에 이미 등재돼 있으면

지적 대상이 **PR diff 안 문서**(spec.md 미결 표 등)의 미결/오픈이슈 표 행이거나 그
등재문을 인용하면 **등재 커밋을 확인한다.** 대조 대상이 red-team 기록이 아니라 diff 안
문서 자체이므로 **기록 없는 PR 에서도 수행한다** — "기록 없으면 3·4절 건너뜀" 규칙에
걸리지 않는다(#1003 이 바로 기록 없는 docs-only PR 이었다). 분기는 봇의 요구가 무엇인지로
가른다:

- 요구가 **등재/문서화 자체로 충족**되는 경우("이 리스크가 문서화돼 있지 않다" 류
  docs-only 자기참조) → **1번 질문(사실인가)에서 닫힌다.** 요구가 이미 충족됐으므로 사실
  주장이 반박된다 — `already-applied` 로 분류하고 등재 커밋을 짚어 응답한다
- 봇이 **해결을 요구**하는 경우(등재는 됐지만 "고쳐라") → 사실은 맞다. 등재 행은
  **2번 질문(이 티켓에서 고칠 것인가)의 근거**다 — 기존 `out-of-scope` 정의 그대로
  (등재 행이 후속 추적의 근거). 여기에 "already-applied + 등재 커밋"으로 답하면 안 고친
  것을 "이미 반영"이라 말하는 셈이다 — 신뢰 하락과 재게시를 부른다

#### 1번 질문이 레포 밖을 가리키면 — code-hub 로 확인한다 (조건부)

코멘트의 주장이 이 레포의 코드로 확인되지 않는 경우가 있다 — "BE 가 이 필드를 null 로
줄 수 있다", "서버는 이때 409 를 반환한다", "이 SDK 함수의 계약이 다르다" 류.
로컬 코드만 봐서는 기본값("리뷰어가 맞다")을 확인도 반박도 못 한다.

**code-hub MCP 가 연결돼 있으면** (`mcp__code-hub__*` 도구 존재) BE 구현을 직접 본다:
`findApi` / `getApiImplementation` 으로 응답 타입·에러 코드·nullability 를 확인하고,
응답 초안에는 기록이 아니라 **BE 코드를 인용한다** (파일:줄 — 4절의 "코드를 인용한다"
규칙이 레포 경계 너머에도 그대로 적용된다).

인용에는 **`master 기준, 동기화 <시각>` 라벨이 필수다.** code-hub 는 master 의 3시간
증분 스냅샷이라, 리뷰어가 진행 중인 BE PR 을 근거로 말했다면 스냅샷과 다를 수 있다 —
라벨 없이 인용하면 낡은 계약으로 맞는 지적을 반박하는 오류 모드가 생긴다.

code-hub 가 없거나 주장이 미머지 BE 변경에 관한 것이면 추측하지 않는다 — 4절의
규칙대로 **사용자에게 올린다.** 새 필수 의존이 아니다.

### 3. 기록 대조 — 소수 케이스를 걸러낸다

스크립트가 `의사결정 기록:` 으로 라운드 디렉토리를 알려준다. `context.md` 를 읽는다 —
아래 표의 왼쪽이 코멘트 성격이고 오른쪽이 그 근거가 있는 절이다.

| 코멘트 성격 | 근거 |
|---|---|
| 이미 검토하고 기각한 대안을 다시 권함 | `### 기각한 대안` |
| 이 티켓 범위 밖으로 분리한 것 | `## 스코프 밖` · `decisions.md` → `## 후속 티켓` |
| 이미 반영한 것을 다시 지적 | `## 이미 반영된 지적` |
| 기획·정책이 확정된 것을 되물음 | `### 기획·…확인 완료 사항` |
| 설계 축을 깨는 제안 | `### 불변식` |
| 내가 이미 철회한 주장을 리뷰어가 꺼냄 | `decisions.md` → `### 철회한 주장` |
| **어디에도 없음** | 새 지적 — 대조할 게 없으니 코드로 판정한다 |

### 4. 근거 재확인 — 드물게 발동하지만 틀렸을 때 비싸다

**기록은 "이미 고려했다"의 증거일 뿐 "옳다"의 증거가 아니다.**

이 구분을 놓치면 스킬이 반박 기계가 되고, 맞는 지적을 "이미 기각함"으로 밀어낸다. 그건 리뷰어의
신뢰를 깎는 가장 빠른 길이다. 실측 35건 중 이 함정이 발동할 수 있었던 것은 1건뿐이지만,
**그 1건이 실제 결함이었다** — 기록에 `settleToNull short-circuit 이미 고침` 이라 적혀 있었는데
고쳐진 것은 optional 쪽이고 critical 대 critical 은 남아 있었다. 한 문구가 두 결함을 덮고 있었다.

같은 성질의 사례가 red-team 에도 있다 — 계획 게이트가 자기 계획을 리뷰해 3건을 잡았고 그중
2건이 기존 분석을 뒤집었다(소비처 오판, 도달 가능성 전제 오류).

빈도는 낮고 비용은 높다. 그래서 자동화하지 않고 **매번 코드를 확인한다.**

기록에 걸린 코멘트라도 **그대로 반박하지 않는다.** 순서는 이렇다:

1. 기록이 그 지적을 다룬 근거를 **코드에서 다시 확인한다** — 파일을 열고, 호출부를 찾고,
   값이 실제로 어떻게 흐르는지 본다
2. 근거가 지금도 유효하면 → 그 근거를 인용해 응답한다(기록을 인용하는 게 아니라 **코드를** 인용한다)
3. 근거가 틀렸거나 상황이 바뀌었으면 → **리뷰어가 맞다.** 새 지적으로 취급한다
4. 확인이 안 되면 → 사용자에게 올린다. 추측으로 반박하지 않는다

`context.md` 자체가 이걸 알고 있다: *"기각한 대안 — 다시 권하지 말 것, 기각 근거가 사실오류일 때만 지적"*.
그 조건절이 여기 그대로 적용된다.

### 5. 분류

**빈도는 과거 PR 30개·2레포(리뷰 570건·응답 133건) 실측이다.** 합이 100%를 넘는 것은
**한 코멘트에 판정이 겹칠 수 있기 때문**이다 — 특히 `out-of-scope` + `real-defect`(맞는 지적이지만
이 PR 에서는 안 고친다)가 흔하다. 하나만 고르라고 강제하면 2절의 두 질문이 다시 뭉개진다.

| 분류 | 빈도 | 다음 행동 |
|---|---|---|
| `real-defect` | **82.7%** | 고쳐야 함 → 6절. 사실 판단의 기본값 |
| `already-applied` | **14.3%** | 반영 커밋을 짚어 응답. `+Nc` 가 크면 대개 이것이다 |
| `out-of-scope` | **22.6%** | 후속 티켓 번호와 함께 응답. 없으면 티켓 신설을 제안. **실측에서 가장 많이 놓친 분류다** |
| `duplicate` | **1.5%** | 같은 지적을 앞선 응답에서 이미 처리 — **그 코멘트 URL 을 링크**해 답한다. 코드가 아니라 내 이전 응답을 가리키는 점이 `already-applied` 와 다르다 |
| `counter-proposal` | **2.3%** | 결함은 인정하되 제안된 해법·수치는 채택하지 않는다. **데이터·근거를 들어** 대안을 제시한다 |
| `by-design` | **3.8%** | 의도된 동작. 왜 그렇게 뒀는지 층위를 설명한다. 후속 티켓도 아니고 결함도 아니다 |
| `already-rejected` | ~0 | 기각 근거를 **코드로 확인한 뒤** 응답 (4절) |
| `reviewer-mistaken` | **0.8%** | 리뷰어가 코드를 잘못 읽음 — 근거를 보여주고 정정 |
| `taste` | ~0 | 결함이 아님 — 판단을 사용자에게 올린다. 스킬이 대신 기각하지 않는다 |
| `no-response-needed` | — | LGTM·봇 안내 등 |

`already-rejected`·`taste` 는 133건에서 한 번도 안 나왔고 `reviewer-mistaken` 은 1건이다.
셋 다 "리뷰어가 틀렸다"는 주장이라 **여기에 넣으려는 충동이 들면 먼저 `real-defect` 가 아닌지 다시 본다.**

반대로 **`out-of-scope` 는 과소 적용된다** — 블라인드 측정에서 놓친 6건 중 4건이 이것이었다.
"맞는 지적"이라고 판단한 순간 범위 확인을 건너뛰기 때문이다. 2절의 두 번째 질문을 빼먹지 않는다.

`already-applied` 에는 docs-only 자기참조라는 사례가 하나 더 있다 — 봇이 "이 리스크가
문서화돼 있지 않다"고 지적했는데 그 리스크가 **PR diff 안 문서의 미결 표에 이미 등재**된
경우다(2절의 등재 대조 — Q1 에서 닫힌다). 등재 커밋을 짚어 응답한다. 단, 봇이 등재가 아니라
**해결**을 요구했다면 `out-of-scope` 다 — `already-applied` 로 답하면 안 고친 것을
"이미 반영"이라 말하는 셈이다.

### 5-1. 분류 확인 — 수정 전 사람 게이트

분류가 끝나면 **한 화면으로 보여주고 승인받는다.** 코멘트가 5건이면 5번 묻는 게 아니라 한 번이다.

스코프 밖 목록을 같이 띄운다 — 사람이 대조할 입력이다:

```bash
python3 ~/.claude/skills/pr-triage/scripts/fetch_comments.py --pr <N> --new-only --show-scope
```

확인 화면은 이 형태로 낸다.

```
[real-defect]      #5112608871  재시도 버튼이 클라이언트 쿼리를 재조회하지 않음
                   근거: RetryNotice.tsx:25 가 router.refresh() 만 호출 · errored useQuery 는 재조회 안 됨
                   범위: 스코프 밖 목록과 겹치지 않음
[out-of-scope]     #5113623641  critical 실패 시 optional 타임아웃 대기
                   근거: 변경 전에도 동일 (user.server.tsx 는 당시 resolve null)
                   범위: `F9 mutex 대기열 증폭` 과 같은 계열 → TICKET-XXX
[by-design]        #5114121080  …
                   미루는 이유: …
```

**`out-of-scope`·`by-design`·`counter-proposal` 로 분류한 것은 "미루는 이유"를 한 줄 필수로 쓴다.**
쓸 수 없으면 그건 `real-defect` 다. 반대로 `real-defect` 에는 **범위 확인 결과를 한 줄 쓴다** —
스코프 밖 목록의 어느 항목과도 겹치지 않는다는 것을 명시한다. 이 한 줄을 못 쓰면 확인을 건너뛴 것이다.

사용자가 분류를 고치면 그대로 따른다. 승인이 나면 **결과를 기록하고** 6절로.

`no-response-needed` 로 승인된 코멘트는 회신이 없어 8절의 게시 후 커서 갱신을 타지
않는다 — **분류 승인 직후 `--mark-triaged` 로 종결한다.** 안 하면 `--new-only` 가 계속
반환해 다음 라운드가 같은 코멘트를 재처리하고, 9절의 "미처리 코멘트가 남아 있으면
그것부터" 판단도 흐려진다.

```bash
python3 ~/.claude/skills/pr-triage/scripts/fetch_comments.py --pr <N> --log-classification \
  '[{"id":123,"predicted":["real-defect"],"confirmed":["out-of-scope","real-defect"],"note":"사용자 교정"}]'
```

**이 한 줄이 스킬을 스스로 개선시킨다** — 아래 절 참고. 교정된 건이 값진 신호이므로
승인만 된 것도 같이 기록한다(둘의 비율이 정확도다).

### 6. 수정 — 승인된 분류대로 고친다

`real-defect` 로 승인된 것을 **직접 고친다.** 다만 고치고 바로 회신하지 않는다. 순서가 정해져 있다:

1. **수정한다.** 여러 코멘트가 같은 근본 원인이면 표면별로 패치하지 말고 **불변식 하나로 수렴**시킨다 —
   표면별 패치는 다음 라운드에 다른 표면을 부른다
2. **검증한다.** 저장소의 typecheck / lint / test 를 돌린다. 빌드가 필요한 변경이면 빌드까지
3. **`red-team` 코드 게이트를 통과시킨다.** 이게 수정을 자동화할 수 있는 근거다 —
   내 수정이 새 회귀를 만들었는지 같은 기준으로 검증된다. NO-GO 면 회신하지 않고 라운드를 더 돈다.
   `INVALID` 는 GO 가 아니다 — 리뷰어가 전원 결과를 못 낸 것이니 엔진을 확인하고 다시 돈다
4. GO 가 나면 7절로

**게이트를 건너뛰고 회신하지 않는다.** 검증 안 된 수정에 "고쳤습니다"를 붙이면 그 말이 PR 에
남고, 틀렸을 때 리뷰어가 두 번 지적해야 한다.

컨텍스트는 이미 라운드에 있으니 `## 리뷰 대상`·`## 검증 상태` 두 절만 이번 수정 기준으로 갱신한다
(`resume.py --next code` 가 나머지를 이관한다).

### 6-1. 처리 결과를 red-team 기록에 넣는다

`decisions.md` 에 넣으면 **다음 라운드 컨텍스트로 자동 이관되어 재제기가 막힌다.** 절을 잘못
짚으면 이관이 조용히 누락되므로 손으로 붙이지 말고 스크립트를 쓴다.

```bash
python3 ~/.claude/skills/pr-triage/scripts/record_decisions.py \
  --round-dir <라운드 경로> --items <items.json> --label "PR #<N> 리뷰 코멘트 처리"
```

`items.json` 은 `[{"section": "반영|후속 티켓|보류", "text": "- …"}]` 이고 `--dry-run` 으로
먼저 확인할 수 있다. 분류별 대응: `real-defect` → `반영`, `out-of-scope`·`counter-proposal`·`by-design`
→ `후속 티켓`(또는 판단 근거를 남긴다), 사용자 판단이 필요한 `taste`·확신 없는 건 → `보류`.

**한 코멘트가 `real-defect` + `out-of-scope` 둘 다면 양쪽에 적는다** — 고친 부분은 `반영`,
미룬 부분은 `후속 티켓`. 이렇게 갈라 두면 다음 라운드에 어느 쪽도 재제기되지 않는다.

**`보류` 에 항목을 넣으면 red-team 이 다음 라운드로 넘어가지 않는다** — 의도된 차단이다.

기록되는 형태:

```markdown
## 반영 — 다음 컨텍스트의 `이미 반영된 지적` 이 된다

### PR #872 리뷰 코멘트 처리
- [Jinwoong-Hwang, comment 5112608871] 재시도 버튼이 클라이언트 쿼리를 재조회하지 않음
  → useUser 의 invalidate 를 4개 호출부에 연결 (커밋 abc1234)

## 후속 티켓 — 다음 컨텍스트의 `스코프 밖` 이 된다

### PR #872 리뷰 코멘트 처리
- [comment 5113623641] critical 실패 시 optional 타임아웃 대기 → pre-existing, TICKET-XXX 신설
```

`## 반영` / `## 후속 티켓` 절 안에 넣으면 `resume.py --next` 가 다음 컨텍스트로 자동 이관한다.

red-team 코드 게이트 GO 가 작업 B(티켓/이슈 AC 코멘트 — red-team 「게이트 GO 후」 절)를
발동시키는 경우, **이 기록이 그 초안보다 먼저다** — 기록 전에 초안을 만들면 이번 수정분의
커밋·근거가 AC 코멘트에서 빠진다.

**미결 등재를 diff 안 문서로 옮겨 적는 것에는 부작용이 있다.** decisions.md 의 수렴 장치는
context.md 를 읽는 자기 리뷰어에게만 작동한다. 같은 내용을 diff 안 문서(spec.md 미결 표
등)로 옮겨 적으면 외부 봇에게는 지적 표면적이 된다(#1003 실측 — 등재 직후 46건). 외부
봇이 리뷰하는 PR 에서는 미결 목록을 diff 밖(티켓·PR 본문)에 두는 것을 우선 고려한다.

### 7. 응답 초안

**분류당 한 건씩 초안을 만들어 사용자에게 보여주고 승인받는다.** 자동 게시하지 않는다 —
잘못된 반박은 조용히 남고 리뷰어와의 신뢰를 깎는다. 되돌리기가 코드보다 어렵다.

응답 형태는 이 저장소에서 이미 통하는 패턴을 따른다:

```
판정 한 줄 → 근거(파일:줄, 실제 값·조건) → 무엇을 했나(커밋 해시)
```

- **맞는 지적은 맞다고 먼저 말한다.** "지적이 맞습니다" 로 시작하고 변명하지 않는다
- 여러 지적이 한 코멘트에 있으면 번호를 그대로 살려 각각 답한다. 하나만 답하면 나머지가 재제기된다
- 회귀가 아니라고 판단했으면 **왜 아닌지**를 코드로 보인다("변경 전에도 동일" 만으로는 부족하다 —
  변경 전 그 경로가 실제로 무엇을 했는지 쓴다)
- 사과·수식어를 붙이지 않는다. 리뷰어가 필요한 것은 판정과 근거다

**같은 지적이 답변 후에 또 올라오면** — 이 문단은 **사람 리뷰어 한정**이다. 사람의 재제기는
응답을 다시 쓸 일이 아니라 납득할 근거가 빠졌다는 신호다 — 말을 바꾸지 말고 **코드와 커밋을
짚어** 다시 답한다. 봇은 다르다 — 아래 소절을 따른다.

#### 봇 리뷰어 분기 — fp 가 있는 봇은 회신이 옳아도 재게시한다

hermes 류 봇은 코멘트에 `<!-- hermes:fp=… -->` fingerprint 마커를 심고 **회신 산문을
소비하지 않는다.** 실측(hermes 계열 594 PR 전수 artifact): 산문 반박은 재게시를 막지
못했고, 종결과 상관을 보인 신호는 👎 리액션뿐이었다(gemini 류는 산문을 소비한다 — 같은
취급을 하면 안 된다). 그래서 **fp 가 있는 봇 코멘트**에는 재게시 프로토콜을 쓴다.
회차는 fetch 출력의 `fp_seq`(1절 `↻N`)가 유일한 진실이다:

- **1회차** — 전문 반박을 게시하고, 오탐이면 👎 리액션을 **동시에** 단다
  (replies.json 항목에 `"reaction": "-1"` — 8절)
- **2회차** — `fp_reply_url`(1회차 회신 링크) 인용 + 3줄 이내 요약. **재반박문을 새로
  쓰지 않는다** — 봇은 산문을 읽지 않으므로 긴 글은 낭비고, 1회차 앵커가 진실이다
- **3회차 이후** — 사용자에게 "봇 종결 불가"를 보고하고 해당 fp 에는 회신을 중단한다.
  재게시 텔레메트리(`pr-triage-reposts.jsonl`)는 계속 쌓인다 — 그 누적이 봇 팀에 종결
  경로 신설을 요청할 근거다

**👎 지시를 fp 있는 봇으로 한정하는 근거**: 👎=종결 신호 실측(artifact) 자체가 hermes
계열이고, fp 없는 봇(aws-security-agent 류)에 👎 를 단 실사용은 #9588(32건)·#1003(106건)
전수에서 0건이다 — post_replies 의 `fps` 필수 게이트와 이 지시가 일치한다. 사람 리뷰어
코멘트에는 리액션을 지시하지 않는다(같은 게이트가 막는다). aws 류 봇 리액션이 필요해지면
그때 `bot` 필드 확장으로 푼다 — 지금은 스코프 밖이다.

**회신 본문에 fp 마커·봇 서명(선두 🤖·auto-review 서명 주석)을 넣지 않는다 — fps 는
replies.json 필드로만 나른다.** 봇 본문을 raw 로 인용해 올리면 내 회신이 '리뷰'로
오분류되어 커서가 후퇴하고 fp_seq 가 부풀고 감시가 내 회신을 알린다. post_replies 가
게시 전에 같은 `is_bot` 판정으로 거부한다 — 인용이 필요하면 blockquote(`>`)로 한다.

**수동 앵커 폴백은 증상 기반이다.** fp 가 `fp_replied` 아님인데 목록에 내 과거 회신이
보이면 — 원인 불문(이 기능 배포 전의 회신, 게시 후 크래시로 일괄 기록 유실, red-team
미발견으로 기록 스킵) — 과거 회신을 찾아 그 링크로 앵커하고 상태 파일의 `fp_replies` 를
수동으로 백필한다. 시간 인접성으로 기계 백필하지 않는다 — 잘못 이은 앵커는 잘못된 링크를
이후 회신마다 재생산한다.

### 8. 게시

승인된 초안만 JSON 으로 모아 올린다. **기본이 dry-run 이고 `--confirm` 이 있어야 실제로 올라간다.**

```bash
python3 ~/.claude/skills/pr-triage/scripts/post_replies.py \
  --repo owner/name --pr N --replies <replies.json>            # 미리보기
python3 ~/.claude/skills/pr-triage/scripts/post_replies.py ... --confirm
```

`source: inline` 은 그 코멘트 스레드에 답글로 붙고, top-level·review 는 PR 에 새 코멘트로 올라간다.

replies.json 항목에는 선택 필드가 둘 있다 — `fps`(이 회신이 다루는 fingerprint **문자열**
리스트. fetch 출력의 fps 에서 **fp 값만** 복사한다 — 객체 배열을 통째로 붙이면 검증에서
거부된다)와 `reaction`(`"-1"`/`"+1"` — fps 가 있는 항목에만 허용, 7절의 봇 리뷰어 분기).
게시가 끝나면 스크립트가 항목의 fps 전원을 상태의 `fp_replies` 에 일괄 기록한다
(keep-first — 1회차 앵커를 덮지 않는다). 회신 본문이 봇 판정(`is_bot`)에 걸리면 게시 전
검증이 거부한다 — 7절의 금지 문구가 그 이유다.

게시가 끝나면 **커서를 갱신한다** — 안 하면 다음 라운드에 같은 코멘트를 또 처리한다:

```bash
python3 ~/.claude/skills/pr-triage/scripts/fetch_comments.py \
  --pr <N> --mark-triaged "<처리한 코멘트 id 쉼표 구분>"
```

그리고 0절의 감시로 돌아간다.

### 9. approve·LGTM 후 — PR 본문을 최신화한다

pr-triage 를 도는 동안 코드가 바뀌는데 PR description 은 `zax:pr` 이 처음 만든 상태에
멈춰 있다 — 머지 시점의 PR 본문이 실제 변경과 다르다. 그래서 PR 이 approve·LGTM 을 받은
시점에 본문을 실제 변경 기준으로 맞춘다. 이 단계는 red-team 컨텍스트의 `## 티켓` 절과
무관하다 — 대상이 티켓이 아니라 PR 본문이고, PR 번호는 이 스킬이 이미 알고 있다.

**트리거는 기계 조건이 아니라 사람 신호다.** 안내를 여는 신호는 둘이다.
① **수집 목록의 승인 신호** — `<APPROVED>` review state, 또는 **사람 리뷰어**의 명시적
승인 문구(LGTM·승인 등). 조건부 승인("~ 고치면 LGTM")은 남은 지적을 먼저 처리한 뒤
안내한다. 봇의 LGTM·이모지 리액션은 신호가 아니다. 판단은 모델이 본문으로 한다 —
오탐 비용은 안내 한 번이다. ② **사용자의 직접 지시** — 본문 없는 표준 Approve 는
수집기·감시기에 뜨지 않으므로(수집기는 본문 있는 리뷰만 나른다), 사용자가 "approve
받았어" 라고 알려주는 것이 그 경우의 신호다. 빈 APPROVED 의 수집기 표시는 후속 개선
후보다. 신호가 보이면 사용자에게 "PR 본문을 실제 변경 기준으로 최신화할까요"를 안내하고,
**실행하라고 할 때** 수행한다 — "미처리 0" 같은 상태 조건으로 자동 발동하지 않는다.
상태 판정으로 발동 시점을 정하면 그 판정의 엣지(실패·무변경·승인 대기)마다 감시 수명
규칙이 따라붙는데, 발동 시점은 사용자가 가장 잘 안다. 미처리 코멘트가 남아 있으면
그것부터 처리한다. `no-response-needed` 만 남은 상태는 미처리로 세지 않는다(5-1 의
`--mark-triaged` 종결이 전제다). **이 단계는 감시의 수명을 건드리지 않는다** — Monitor 는
0절 규칙대로 계속 돌고, 본문 최신화 뒤에 새 코멘트가 오면 새 라운드로 처리한다.

**반영하는 것은 실제로 코드가 바뀐 것뿐이다** — 이 브랜치 라운드 디렉토리 **전체**의
`decisions.md` 를 순회해 `### PR #N 리뷰 코멘트 처리` 라벨이 붙은 `반영` 항목과 그
커밋들을 모으고 중복을 걷어낸다. 트리아지가 여러 라운드를 돌았으면 반영분이 여러 라운드에
흩어져 있다 — 마지막 라운드만 보면 이전 라운드의 코드 변경이 본문에서 빠진다. 회신만 하고
코드가 안 바뀐 분류(`already-applied`·`out-of-scope`·`counter-proposal`·`by-design`)는
PR 본문에 넣지 않는다 — **PR 본문은 변경 요약이지 리뷰 응답 로그가 아니다.** 반영 항목과
후속 티켓 분리분이 **모두** 0 건이면(전부 반박·by-design 으로 끝난 PR) 아무것도 하지
않는다 — 후속 티켓이 있으면 코드 변경이 없어도 그 한 줄은 본문에 남긴다.

**후속 티켓으로 뺀 항목은 한 줄로 남긴다** — 리뷰어가 "이건 어디 갔나"를 다시 묻는 것을
막는 자리다 (6-1절 말미의 "미결 목록을 diff 밖에 둔다"가 가리키는 그 자리이기도 하다).
수집 규칙은 `반영` 과 같다 — 브랜치 라운드 전체의 `decisions.md` 에서 같은
`### PR #N 리뷰 코멘트 처리` 라벨 아래 `후속 티켓` 항목을 모으고 중복을 걷어낸다.
단, 수집 대상은 **실제로 별도 티켓으로 분리했거나 신설이 확정된 항목**(티켓 키 또는
"신설 예정" 명시)뿐이다 — 6-1 은 by-design·반박류의 판단 근거도 이 절에 남기는데,
그런 항목은 후속 티켓 개수와 본문 초안 양쪽에서 제외한다.

절차 — **PR 번호와 저장소는 수집 시점에 확정해 끝까지 인자로 고정한다**(지연 실행 시
cwd·브랜치가 바뀌어 있으면 인자 없는 `gh pr` 명령이 현재 브랜치의 다른 PR 을 고른다):
`gh pr view <N> -R <owner/repo> --json body` 로 현재 본문을 읽고 → 수집한 `반영`·`후속 티켓` 항목이
본문에 없거나 본문의 기존 서술과 상충하면 해당 구역만 갱신한 초안을 만든다. 초안을 만들 때
**입력 스냅샷을 보존한다** — 그 시점 PR 코멘트의 정규화 레코드(`source + id + body +
state`, 가능하면 `updated_at`) 집합, 초안에 쓴 `반영`·`후속 티켓` 목록, 그리고 PR head
커밋(`headRefOid`). ID 만 모으면 승인 대기 중 기존 코멘트가 **편집**된 것("LGTM" →
"LGTM 취소")을 못 보고, head 를 안 보면 승인 대기 중 push 된 커밋(반영분 되돌림 등)을
못 본다. → 사용자에게
`변경 전 → 변경 후` 를 보여주고 승인받고 → **게시 직전 재확인은 커서가 아니라 스냅샷 대
현재 상태의 대조다** (커서는 브랜치 디렉토리 기반이라 승인 대기 중 cwd·브랜치가 바뀌면
엉뚱한 것을 읽고, `--new-only` 는 다른 세션이 종결한 코멘트를 숨긴다):
① 본문 재조회 — 달라졌으면 게시하지 않고 재대조해 다시 승인받는다(red-team 공통 규칙과
같다) ② 코멘트 대조 — `<N> -R <owner/repo>` 로 전체 목록을 다시 받아 스냅샷과 동등
비교한다. 추가·삭제·본문·상태 변경 중 하나라도 있으면 초안을 폐기하고 트리아지 loop 로
돌아간다
③ 반영분 대조 — decisions.md 를 재순회해 초안의 입력 목록과 다르면(그 사이 다른 세션이
처리분을 기록) 초안을 폐기하고 새 초안으로 다시 승인받는다 ④ head 대조 —
`headRefOid` 가 스냅샷과 다르면(승인 대기 중 push) 초안을 폐기하고 재작성·재승인한다
→ 전부 통과하면
`gh pr edit <N> -R <owner/repo> --body-file <tmp>` 로 게시한다. `zax:pr` 이 만든 섹션 구조를
깨지 않는다 — 기존 섹션에 항목을 더하거나, 맞는 자리가 없으면 마지막에 `## 리뷰 반영`
섹션을 새로 만든다.

공통 규칙은 red-team 의 「게이트 GO 후 — 외부 산출물 최신화」 절과 한 벌이다:

- **승인 없이 write 하지 않는다.** 승인 요청은 한 번에 하나의 산출물만 다룬다.
  자동 게시는 옵션으로도 만들지 않는다.
- **읽기 → 대조 → 변경 없음이면 조용히 종료.** 빈 편집을 게시하지 않는다.
- **실패는 흐름을 막지 않는다 — read 실패와 write 실패는 처리가 다르다.** 최초
  read(`gh pr view`)가 실패하면 초안 자체를 만들 수 없다 — 현재 본문을 추측하지 말고
  반영 예정 항목의 요지만 출력한다. write(`gh pr edit`) 실패면 그 사실과 게시하려던
  초안 전문을 출력해 사용자가 손으로 붙일 수 있게 한다. 어느 쪽이든 초안/요지를 사람에게
  인계한 것으로 이 단계는 끝난다 — 자동 재시도는 없고, 사용자가 다시 실행하라고 하면
  처음부터 다시 밟는다. 감시는 0절 규칙대로 그대로 돈다.

## 의사결정 기록이 없는 PR

과거 PR, 남이 만든 PR 을 이어받은 경우, `red-team` 을 거치지 않은 변경 — 기록이 없어도 동작한다.
스크립트가 `의사결정 기록: 없음` 을 알려주고, 그때는 3·4절을 건너뛰고 **코드로만 검증**한다.
분류 카테고리는 그대로 쓰되 `already-rejected` / `already-applied` 는 커밋 이력에서 근거를 찾는다.

기록 없음을 이유로 멈추지 않는다 — 기록은 대조를 싸게 만드는 것이고, 없으면 원래 방식대로
코드를 읽으면 된다.

## 경계

- **내가 리뷰어가 되어 남의 PR 을 읽고 코멘트를 만드는 것은 `review-buddy`** 다. 방향이 반대다
- 수정은 이 스킬이 하고, **검증 게이트는 `red-team` 을 호출해서** 쓴다(루프 로직을 복제하지 않는다)
- loop 는 `Monitor` 도구가 한다. 이 스킬은 감시기·커서만 제공한다
- PR 생성·배포는 `fix-flow` 7~9단계다

## 측정 — 이 문서의 수치는 어디서 왔나

**`evals/` 의 도구는 저장소에 있고, 채점 데이터는 없다.** 채점 대상(내 과거 PR 응답)과
오염 목록은 로컬 자산(`~/.red-team/eval/`)이라 남의 환경에서는 표본 없이 도구만 남는다.
그래서 **네 저장소를 대상으로 직접 수집해서 다시 재면 된다** — 아래 도구가 그 일을 한다.
이 문서의 수치는 저자 환경에서 나온 것이고, 근거는 이렇다(2026-07-29).

| 도구 | 하는 일 |
|---|---|
| `harvest_replies.py` | 과거 PR 에서 (리뷰 → 내 응답) 쌍을 모아 **실제 분류 분포**를 낸다. 내 과거 응답이 정답 라벨이다 |
| `make_blind_set.py` | **정답을 가린** 문항을 만든다. 응답을 보면서 분류하면 정확도가 아니라 독해력을 잰다. `--exclude-prs` 로 이미 본 PR 을 뺀다 |
| `score.py` | 분류 채점 — strict/overlap + **안전 지표 두 개**(반박 오분류 / 스코프 크립) |
| `score_drafts.py` | 초안 채점 — 과거 응답이 담았던 요소(판정 명시·커밋 인용·코드 근거·번호 대응)를 초안이 담았는지 |

**오염 목록은 `~/.red-team/eval/pr-triage/CONTAMINATED.md` 에 있다.** 정답을 이미 읽은 PR 이고
`--exclude-prs` 에 그대로 넣는다. 조사 중 응답 본문을 출력하면 그 PR 을 이 목록에 추가한다 —
표본이 부족해지면 오염된 PR 을 재사용하지 말고 레포·스캔 범위를 넓힌다(org 전체 1631 PR).

```bash
python3 evals/harvest_replies.py --repos <org>/<repo-a>,<org>/<repo-b> --top 30 --out pairs.json
python3 evals/make_blind_set.py --pairs pairs.json --n 20 --exclude-prs "<정답 본 PR>" --out blind.json
python3 evals/score.py --answers answers.json --predictions preds.json
```

**측정이 실제로 고친 것 세 가지** — 이 문서를 바꿀 때 참고한다.

1. **레포를 섞어야 한다.** 저장소 하나만 봤을 때는 봇 판별이 `🤖` 접두어로 충분해 보였는데,
   다른 저장소의 봇은 `<!-- …-pr-auto-review:… -->` HTML 주석을 먼저 붙여서 판별이 뚫렸다.
   리뷰가 "내 응답"으로 오분류돼 loop 이 아예 못 보고 넘어갈 버그였다
2. **분포가 프레이밍을 정한다.** 6 PR 표본에서 57% 였던 `real-defect` 가 30 PR 에서 82.7% 였다.
   초판은 "코멘트 응답의 대부분은 기록과 대조하는 일"이라고 썼는데 실측이 반박했다
3. **안전 지표가 하나로는 부족했다.** 처음엔 "맞는 지적을 반박으로 분류"만 봤고 그건 0건이었다.
   그런데 반대 방향 오류가 6/20(30%) 였다 — 미룰 것을 고칠 것으로 봄. 수정이 자동인 loop 에서는
   이쪽이 스코프 크립을 만든다. 2절의 두 질문 분리가 이 수치에서 나왔다

## 2차 측정 (30 PR → 60 PR·4레포) — 두 결론

**분류 정확도는 overlap 80~85% 에서 멈췄고, 안전 B(미룰 것을 고칠 것으로 분류)는 두 번 모두 30%.**
1차와 2차 사이에 2절의 두 질문 분리를 문서에 써넣었는데 수치가 안 움직였다 —
**절차를 문서에 적는 것과 그 절차를 따르는 것은 다르다.** 그래서 5-1 분류 확인 게이트를 넣었다.
안전 A 도 2차에서 처음 1건 깨졌다(`already-applied` 를 남용). `+Nc` 신호를 문항에 넣어줬더니
1차의 '놓침'이 2차의 '과신'으로 뒤집혔다 — **이 판정 자체가 불안정하다.**

**초안 품질은 쓸 만하다.** 10건 채점: 판정 명시 9/10 · 코드 근거 5/5 · 번호 대응 2/2.
`커밋 인용`(6/7)은 판별력이 없다 — 실제 loop 에서는 수정이 회신보다 먼저라 해시가 구조적으로 확보된다.
실패 2건은 (a) approve 코멘트에 인사로 시작해 판정을 첫 두 문장에 안 넣음 (b) 초안이 정답의 25% 길이
— 근거가 빠졌다는 신호다.

**측정 불가로 결론난 것**: `duplicate`·`counter-proposal`·`reviewer-mistaken` 정확도.
표본을 30→60 PR(4레포)로 늘렸는데 **이 라벨들이 하나도 늘지 않았다**(각 3/2/1 그대로).
실제로 0.6~1.7% 로 희귀한데다 코멘트 많은 PR 에 몰려 있고 그 PR 들이 이미 오염됐다.
깨끗한 쌍은 23개뿐이다. 5건씩 모으려면 200+ PR 을 더 훑어야 하고 오염 위험은 같다 —
이 방법으로는 안 된다. 실사용에서 그 분류가 실제로 문제를 일으키면 그때 개별 사례로 본다.


## 자가 개선 — 확인 게이트가 수집기다

이 스킬의 측정은 두 번 다 오염과 표본 부족에 부딪혔다. 원인은 하나다 —
**정답을 나중에 찾으려 했다.** 과거 응답을 뒤지다 정답을 보고, 드문 라벨은 60 PR 을 훑어도
안 늘었다. 그런데 loop 에서는 순서가 뒤집힌다.

| | eval (사후 수집) | loop (확인 게이트) |
|---|---|---|
| 정답 출처 | 과거 응답을 뒤진다 | **사용자 확인** |
| 오염 | 조사 중 정답을 본다 | **구조적으로 불가능** — 정답이 예측 뒤에 생긴다 |
| 드문 라벨 | 0~2건, 표본 2배로도 안 늘어 | 실사용에서 나올 때마다 축적 |
| 비용 | API 수백 회 + 수집 15분 | **0** — 게이트가 이미 있다 |

### 쌓는 것

5-1 확인 게이트에서 `--log-classification` 으로 `{예측, 확정, 교정여부}` 를
**`~/.red-team/pr-triage-log.jsonl`** 에 append 한다.

**PR별 커서 파일이 아니라 전역 로그다.** 한 PR 은 분류가 4~5건이라(실측 30 PR·133응답)
PR별로 쌓으면 임계값에 영원히 도달하지 않는다. 그리고 이 파일은 `last.json` 처럼
없앤 전역 포인터와 다르다 — **append-only 라 낡을 진실이 없고, 과거 분류는 다른 곳에서
파생할 수도 없다.** 가변 포인터는 지웠지만 이벤트 로그는 정당하다.

쌓인 것은 그대로 채점된다 — 라벨 형태가 이미 맞다(`score.py --log <이 파일>`).
`strict`/`overlap`·**안전 A·B**·확정 라벨 분포가 실사용 누적분에 대해 바로 나오고,
블라인드 표본을 만들 필요도 오염을 관리할 필요도 없다. 채점 도구는 배포판에 없으므로
(위 측정 절 참고) 로그만 쌓아두고 채점은 나중에 붙여도 된다 — 로그가 자산이다.

### 두 번째 신호 — 리뷰어의 재제기

사용자 확인만이 정답이 아니다. **회신 뒤 같은 지적이 다시 올라오면 그 자체가 오분류 신호다.**
특히 `already-applied`·`duplicate` 로 답한 건이 재제기되면 그 판정이 틀렸을 가능성이 높다
(이 두 판정은 실측에서 가장 불안정했다). 이 신호는 이미 수집된 데이터에 있다 —
재제기 코멘트와 `+Nc`. 결과 기반이라 사용자 확인보다 강한 증거다.

단, **fp 추적(1절 `↻N`·재게시 텔레메트리)은 봇 재게시만 잡는다** — 봇은 회신이 옳아도
재게시하므로 그건 오분류 신호가 아니라 봇 종결 실패 신호다(그래서 별도 파일
`pr-triage-reposts.jsonl` 에 쌓이고 채점에도 들어가지 않는다). 이 절의 진짜 신호 —
**사람 리뷰어의 재제기** — 는 여전히 수동 관찰이다.

### 무엇을 자동으로 하지 않는가

**데이터가 쌓여도 SKILL.md 를 자동으로 고치지 않는다.** 미검증 분류기에 쓰기 권한을 주는 것과
같고, 그건 이미 P2 자동 반영을 폐지한 이유다. 자가 개선의 현실적 형태는
**측정은 자동, 반영은 사람**이다.

그리고 반영 수단을 고를 때 이 스킬이 배운 것을 기억한다 —
**지시문에 절차를 적는 것만으로는 행동이 바뀌지 않았다**(2절을 고친 뒤에도 안전 B 가 30% 그대로였다).
수치가 안 움직이면 문서를 더 쓰지 말고 게이트·필수 필드 같은 구조로 옮긴다.

### 언제 묻나 — 임계값이 아니라 트리거로

문서에 "30건이면 재측정"이라고 적어두면 아무도 세지 않는다. 그래서 **기록하는 스크립트가
임계값을 넘는 순간 알린다.** 상태를 따로 두지 않고 `이전 개수 < 임계값 ≤ 이후 개수` 로 판정하므로
정확히 한 번 발동한다.

| 트리거 | 무엇을 볼 수 있나 | 실측 기준 대략 |
|---|---|---|
| **교정 5건** | 구체적 실패 사례 5개 — 패턴이 있나 | 안전 B 30% 이므로 분류 ~17건 ≈ **PR 4개** |
| **누적 30건** | 안전 A·B 비율 (30% 와 5% 는 구분된다) | 분류 4~5건/PR 이므로 **PR 7개** |
| **누적 100건** | 드문 라벨(`duplicate`·`counter-proposal`·`by-design`) | **PR 20여 개** |
| 교정 20건 | 반영 여부를 다시 판단 | — |

발동하면 이 스킬이 **재측정 결과를 보여주고 반영할지 묻는다.** 사용자가 세거나 기억할 일이 없다.

**교정 건수를 총 개수보다 앞에 둔 이유**: 교정 하나가 승인 열보다 정보가 많다. 승인은
"틀리지 않았다"는 약한 신호이고(대충 승인했을 수도 있다) 교정은 **어디서 왜 틀렸는지가 붙은
구체적 사례**다. 그래서 총 30건보다 교정 5건이 먼저 온다.

임계값 전에는 손대지 않는다 — 검증할 표본이 없을 때 분류기를 고치는 것이 이 스킬이 피하려는 실수다.
값을 바꾸려면 `scripts/fetch_comments.py` 의 `REVIEW_AT_TOTAL`·`REVIEW_AT_CORRECTED` 다.

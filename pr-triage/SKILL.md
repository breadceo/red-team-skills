# pr-triage

## 필요한 것 — `red-team` 은 필수 의존이다

| 무엇 | 왜 |
|---|---|
| `red-team` 스킬 | 트리아지 상태·의사결정 기록이 같은 `~/.red-team/runs2/<repo>/<branch>/` 를 쓴다 — 경로 복제 시 처리 기록이 조용히 사라진다 |
| `red-team` 0단계 완료 | 6절 코드 게이트가 `run_round.py` 를 부른다 |
| `gh` CLI 인증 | 수집·회신이 전부 `gh api` 다 |
| code-hub MCP (선택) | 레포 밖 계약 주장 확인 — 없으면 그 건은 사용자에게 올라간다 |

`red-team` 은 같은 저장소에 형제로 있다 — 같이 설치하고 **같은 위치에 둔다.** 스크립트는
현재 배포본의 형제만 찾고, 못 찾으면 멈춘다. 전역·대상 저장소의 다른 설치본으로 fallback하지 않는다.

## 왜 이 스킬이 있나

PR 리뷰 대응의 기계적 부분(수집·리뷰어 판별·리뷰가 본 커밋 확인·응답 형식)을 기계에
넘기고, 판단에는 `red-team` 기록을 근거로 쓴다. **기록 대조가 주된 일은 아니다** — 응답의
82.7%가 "지적이 맞습니다"였다. 기록은 **"이 티켓에서 고칠 것인가"** 의 근거이고, 사실
판단을 대신하지 않는다.

## 흐름

```
┌ 호스트 감시기 ── 신규 없으면 아무 일도 없다
↓
신규 코멘트 → ① 사실인가(코드) → ② 이 티켓 범위인가(기록) → 분류
→ ⚠ 분류 확인(라운드당 1회) → real-defect 수정 → 검증 → red-team 코드 게이트 GO
→ decisions.md 기록(6-1) → 회신 초안 → ⚠ 게시 승인 → 게시 → 커서 갱신 ─┘
→ approve·LGTM 관측 → 본문 최신화 안내 → (사용자 지시 시) 9절
```

**사람 게이트가 둘이다: 분류 확인과 게시 승인.** 둘 사이는 사람 없이 간다. 분류 확인은
"미룰 것을 고침" 30% 오류를 **사람이 30초에 걸러내는 위치**로 옮긴 것이다(근거:
`references/measurement.md`).

### 0. 감시 걸기

**`references/monitoring.md`를 읽고 현재 호스트의 한 분기만 실행한다.** Claude Code,
Codex Desktop, 장기 실행 CLI의 exact 경로가 다르다. 없는 도구를 추측하지 않는다.

### 1. 수집

```bash
python3 "<pr-triage-skill>/scripts/fetch_comments.py" --pr <N> --new-only
```

커서 기준 **미처리** 코멘트만 나온다(PR·저장소 생략 시 현재 브랜치). 커서는
`pr-<N>-triage.json` 의 `notified`/`triaged` — 알림 직후 세션이 죽어도 처리 대상이 남는다.

출력의 표시: `→` 내 마지막 응답 이후 코멘트(앞쪽도 부분 응답일 수 있다) /
`+Nc` 그 코멘트 이후 푸시된 커밋 수(크면 낡은 코드를 본 리뷰 — **해당 커밋 먼저 확인**) /
`↻N` 봇 fingerprint 재게시 회차(**`fp_seq` 가 유일한 진실** — 산문·기억으로 세지 않는다.
2 이상이면 봇 분기: `references/edge-cases.md`) / `∉diff`·`∉hunk` inline 코멘트가 변경
범위 밖(**표시일 뿐 걸러내지 않는다**). diff 플래그는 inline 전용 — top-level 봇 코멘트의
범위 대조는 `--show-files` 목록과 본문 속 경로를 모델이 한다.
**작성자 계정으로 올라오는 리뷰가 있다**(사내 봇) — `🤖` 마커(`--bot-marker`)와 그보다
강한 **fp 마커**로 가른다. `<APPROVED>` 리뷰도 실질 지적이 있을 수 있어 본문을 확인한다.

### 2. 두 질문을 따로 묻는다 — "맞나"와 "여기서 고칠 것인가"

**사실 판단의 기본값은 "리뷰어가 맞다"**(82.7%). **그러나 범위 판단까지 덮으면 안 된다** —
"맞으니 고친다" 직행이 30% 오류의 전부였다. 코멘트마다 순서대로:

1. **사실인가?** — 코드로 확인한다. 기본값은 "맞다"
2. **이 티켓에서 고칠 것인가?** — `## 스코프 밖`·후속 티켓과 대조. 사실이어도 범위 밖은
   `out-of-scope` 다

두 답은 독립이다 — `["out-of-scope","real-defect"]` 겹침이 정상 판정으로 흔하다.
**조건부 분기 — 해당하면 `references/edge-cases.md` 의 그 절을 읽는다:** docs-only
diff / diff 안 문서의 미결 표에 등재된 지적 / 레포 밖(BE 계약·SDK) 주장.

### 3. 기록 대조 — 소수 케이스를 걸러낸다

스크립트가 `의사결정 기록:` 으로 라운드 디렉토리를 알려주면 `context.md` 를 읽는다:

| 코멘트 성격 | 근거 |
|---|---|
| 기각한 대안을 다시 권함 | `### 기각한 대안` |
| 범위 밖으로 분리한 것 | `## 스코프 밖` · `decisions.md` → `## 후속 티켓` |
| 이미 반영한 것을 다시 지적 | `## 이미 반영된 지적` |
| 확정된 기획·정책을 되물음 | `### 기획·…확인 완료 사항` |
| 설계 축을 깨는 제안 | `### 불변식` |
| 내가 철회한 주장을 꺼냄 | `decisions.md` → `### 철회한 주장` |
| **어디에도 없음** | 새 지적 — 코드로 판정한다 |

### 4. 근거 재확인 — 기록은 "고려했다"의 증거지 "옳다"의 증거가 아니다

기록에 걸린 코멘트라도 **그대로 반박하지 않는다** — 근거를 코드에서 재확인하고, 유효하면
**코드를** 인용해 응답, 틀렸으면 **리뷰어가 맞다**, 확인 불가면 사용자에게 올린다.
절차·사례: `references/edge-cases.md`(근거 재확인).

### 5. 분류

빈도는 30 PR·2레포 실측. 합이 100%를 넘는 것은 판정이 겹칠 수 있어서다.

| 분류 | 빈도 | 다음 행동 |
|---|---|---|
| `real-defect` | **82.7%** | 고친다 → 6절. 사실 판단의 기본값 |
| `already-applied` | **14.3%** | 반영 커밋을 짚어 응답. `+Nc` 큰 코멘트에 흔함 |
| `out-of-scope` | **22.6%** | 후속 티켓과 함께 응답(없으면 신설 제안). **가장 많이 놓친 분류** |
| `duplicate` | **1.5%** | 앞선 내 응답의 **URL 링크**로 답한다 |
| `counter-proposal` | **2.3%** | 결함 인정, 제안 불채택 — 근거를 들어 대안 제시 |
| `by-design` | **3.8%** | 의도된 동작 — 층위 설명. 후속 티켓도 결함도 아님 |
| `already-rejected` | ~0 | 기각 근거를 **코드로 확인한 뒤** 응답 (4절) |
| `reviewer-mistaken` | **0.8%** | 코드를 잘못 읽음 — 근거를 보여주고 정정 |
| `taste` | ~0 | 결함 아님 — 사용자에게 올린다. 대신 기각하지 않는다 |
| `no-response-needed` | — | LGTM·봇 안내 등 |

"리뷰어가 틀렸다"류(`already-rejected`·`taste`·`reviewer-mistaken`, 실측 합계 1건)에
**넣고 싶으면 먼저 `real-defect` 가 아닌지 다시 본다.** **`already-applied`·`duplicate`
는 가장 불안정한 판정이다** — 커밋이 그 지적을 정말 덮는지 확인한 뒤에만 쓴다.
반대로 **`out-of-scope` 는 과소 적용된다** — 2절의 두 번째 질문을 빼먹지 않는다.

### 5-1. 분류 확인 — 수정 전 사람 게이트

**한 화면으로 보여주고 승인받는다**(코멘트 5건이면 한 번). 스코프 밖
목록(`--show-scope`)을 같이 띄우고, 항목별로 분류·id·요지·근거·범위를 낸다.
**`out-of-scope`·`by-design`·`counter-proposal` 은 "미루는 이유" 한 줄 필수** — 못 쓰면
`real-defect` 다. **`real-defect` 에는 범위 확인 결과 한 줄** — 못 쓰면 확인을 건너뛴
것이다. 교정은 그대로 따르고, 승인이 나면 **결과를 기록하고** 6절로:

```bash
python3 "<pr-triage-skill>/scripts/fetch_comments.py" --pr <N> --log-classification \
  '[{"id":123,"predicted":["real-defect"],"confirmed":["out-of-scope","real-defect"],"note":"사용자 교정"}]'
```

**이 한 줄이 스킬을 스스로 개선시킨다**(`references/measurement.md`) — 승인만 된 것도
기록한다. `no-response-needed` 는 회신이 없어 8절 커서 갱신을 타지 않으므로 **분류 승인
직후 `--mark-triaged` 로 종결한다.**

### 6. 수정 — 승인된 분류대로 고친다

`real-defect` 로 승인된 것을 직접 고치되 순서가 있다: ① 수정(같은 근본 원인이면 표면별
패치가 아니라 **불변식 하나로 수렴**) ② 검증(typecheck/lint/test, 필요시 빌드) ③
**red-team 코드 게이트 통과** — 이게 수정을 자동화할 수 있는 근거다. NO-GO 면 회신 없이
라운드를 더 돌고, `INVALID` 는 GO 가 아니다 ④ GO 면 7절로. **게이트를 건너뛰고 회신하지
않는다** — 검증 안 된 "고쳤습니다"는 PR 에 남는다. 컨텍스트는 `## 리뷰 대상`·`## 검증
상태` 만 갱신한다(나머지는 `python3 "<red-team-skill>/scripts/resume.py" --next code` 가 이관).

### 6-1. 처리 결과를 red-team 기록에 넣는다

`decisions.md` 에 넣으면 **다음 컨텍스트로 자동 이관되어 재제기가 막힌다.** 절을 잘못
짚으면 조용히 누락된다 — 손으로 붙이지 말고 스크립트로:

```bash
python3 "<pr-triage-skill>/scripts/record_decisions.py" \
  --round-dir "<라운드 경로>" --items "<items.json>" \
  --label "PR #<N> 리뷰 코멘트 처리"    # items: [{"section":"반영|후속 티켓|보류","text":"- …"}]
```

대응: `real-defect` → `반영` / `out-of-scope`·`counter-proposal`·`by-design` → `후속
티켓`(판단 근거 포함) / `taste`·확신 없음 → `보류`(다음 라운드를 막는 의도된 차단).
**한 코멘트가 둘 다면 양쪽에 적는다.** 항목은 `[작성자, comment <id>] 요지 → 처리 (커밋)`
형태.

코드 게이트 GO 가 티켓 AC 코멘트(red-team external-sync)를 발동시키면 **이 기록이 그
초안보다 먼저다.** **미결 등재를 diff 안 문서로 옮기면 외부 봇의 지적 표면적이
된다**(#1003 실측) — 미결 목록은 diff 밖(티켓·PR 본문)을 우선 고려한다.

### 7. 응답 초안

**분류당 한 건씩 초안을 만들어 승인받는다. 자동 게시 금지** — 잘못된 반박은 조용히 남고
되돌리기가 어렵다. 형태:

```
판정 한 줄 → 근거(파일:줄, 실제 값·조건) → 무엇을 했나(커밋 해시)
```

- **맞는 지적은 맞다고 먼저 말한다.** 변명하지 않는다
- 한 코멘트의 여러 지적은 번호를 살려 각각 답한다 — 하나만 답하면 나머지가 재제기된다
- 회귀가 아니라고 판단했으면 **왜 아닌지**를 코드로 보인다 — "변경 전에도 동일"만으로는
  부족하다(변경 전 그 경로가 실제로 무엇을 했는지 쓴다)
- 사과·수식어 없이. 리뷰어가 필요한 것은 판정과 근거다

**같은 지적이 또 올라오면** — 사람의 재제기는 납득할 근거가 빠진 신호다. 말을 바꾸지
말고 코드와 커밋을 짚어 다시 답한다. **봇(fp 마커)은 산문을 소비하지 않는다** — 회차별
재게시 프로토콜(`references/edge-cases.md` 봇 리뷰어 분기)을 따른다. **회신 본문에 fp
마커·봇 서명 금지** — 내 회신이 리뷰로 오분류된다. 인용은 blockquote 로.

### 8. 게시

승인된 초안만 JSON 으로 모아 올린다. **기본이 dry-run, `--confirm` 이 있어야 올라간다:**

```bash
python3 "<pr-triage-skill>/scripts/post_replies.py" \
  --repo owner/name --pr N --replies "<replies.json>" [--confirm]
```

`source: inline` 은 그 스레드 답글로, top-level·review 는 새 코멘트로. 선택 필드:
`fps`(fingerprint **문자열** 리스트 — fetch 출력에서 **fp 값만** 복사)와
`reaction`(`"-1"`/`"+1"`, fps 있는 항목에만). 게시 후 fps 가 `fp_replies` 에
기록된다(keep-first). 봇 판정에 걸리는 본문은 게시 전 검증이 거부한다. 게시 후 **커서를
갱신한다** — 안 하면 다음 라운드가 같은 코멘트를 또 처리한다:

```bash
python3 "<pr-triage-skill>/scripts/fetch_comments.py" \
  --pr <N> --mark-triaged "<처리한 코멘트 id 쉼표 구분>"
```

그리고 0절의 감시로 돌아간다.

### 9. approve·LGTM 후 — PR 본문을 최신화한다

트리아지 동안 코드가 바뀌는데 PR 본문은 처음 상태다 — approve 시점에 실제 변경 기준으로
맞춘다(red-team `## 티켓` 절과 무관).

**트리거는 기계 조건이 아니라 사람 신호다** — 수집 목록의 `<APPROVED>`/**사람 리뷰어**의
승인 문구, 또는 **사용자의 직접 지시**("approve 받았어" — 본문 없는 표준 Approve 는
수집기에 안 뜬다). 신호가 보이면 안내만 하고 **실행하라고 할 때** 수행한다 — 자동 발동
금지. 미처리 코멘트가 남았으면 그것부터. **감시 수명은 건드리지 않는다.** 신호 판별과
실행 절차(수집 규칙·스냅샷·`변경 전 → 변경 후` 승인·4단계 재확인·실패 인계)는
**`references/edge-cases.md`(9절 상세)를 읽고 그대로 따른다.**

## 의사결정 기록이 없는 PR

`의사결정 기록: 없음` 이면(과거 PR, 인계, `red-team` 미경유) 3·4절을 건너뛰고 **코드로만
검증**한다 — `already-rejected`/`already-applied` 는 커밋 이력에서 근거를 찾는다. 기록
없음을 이유로 멈추지 않는다.

## 경계

- 내가 리뷰어가 되어 남의 PR 에 코멘트를 만드는 것은 `review-buddy` 다
- 검증 게이트는 `red-team` **호출**로 쓴다 — 루프 로직 복제 금지
- 반복 실행은 호스트 감시기가 한다. 이 스킬은 감시기·커서만 제공한다
- PR 생성·배포는 `fix-flow` 7~9단계다

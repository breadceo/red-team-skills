# 조건부 분기 — 해당 상황이 보일 때만 읽는다

> SKILL.md 의 「참고 문서」에서 참조된다. 각 절 첫머리의 발동 조건이 현재 라운드에
> 해당할 때 그 절만 읽는다.

## diff 가 문서뿐이면 — 기본값 적용 전에 대조를 먼저 통과시킨다

**발동**: PR 의 변경 파일이 전부 문서(docs-only).

82.7% 는 **코드 PR** 실측이다. diff 가 문서뿐이면 실측 유효율이 ~28% 로 역전된다
(product-hub#1003, 94건 중 무효 72% — 자기참조 38.3%·범위 밖 21.3%). 기본값 자체를
"리뷰어가 틀렸다"로 뒤집지는 말되, **`--show-files` 변경 파일 목록과의 대조(범위 밖·유령
라인)와 아래 미결 등재 대조를 먼저 통과시키고** 남는 것에만 기본값을 적용한다.
(스크립트의 diff 플래그는 inline 한정이라 top-level 봇 코멘트에는 적용 0건 — 이 대조는
모델이 한다.)

## 지적 대상이 PR diff 안 문서의 미결 표에 이미 등재돼 있으면

**발동**: 지적 대상이 PR diff 안 문서(spec.md 미결 표 등)의 미결/오픈이슈 표 행이거나 그
등재문을 인용할 때.

**등재 커밋을 확인한다.** 대조 대상이 red-team 기록이 아니라 diff 안 문서 자체이므로
**기록 없는 PR 에서도 수행한다** — "기록 없으면 3·4절 건너뜀" 규칙에 걸리지 않는다
(#1003 이 바로 기록 없는 docs-only PR 이었다). 분기는 봇의 요구가 무엇인지로 가른다:

- 요구가 **등재/문서화 자체로 충족**되는 경우("이 리스크가 문서화돼 있지 않다" 류
  docs-only 자기참조) → **1번 질문(사실인가)에서 닫힌다.** 요구가 이미 충족됐으므로 사실
  주장이 반박된다 — `already-applied` 로 분류하고 등재 커밋을 짚어 응답한다
- 봇이 **해결을 요구**하는 경우(등재는 됐지만 "고쳐라") → 사실은 맞다. 등재 행은
  **2번 질문(이 티켓에서 고칠 것인가)의 근거**다 — 기존 `out-of-scope` 정의 그대로
  (등재 행이 후속 추적의 근거). 여기에 "already-applied + 등재 커밋"으로 답하면 안 고친
  것을 "이미 반영"이라 말하는 셈이다 — 신뢰 하락과 재게시를 부른다

## 1번 질문이 레포 밖을 가리키면 — code-hub 로 확인한다 (조건부)

**발동**: 코멘트의 주장이 이 레포의 코드로 확인되지 않을 때 — "BE 가 이 필드를 null 로
줄 수 있다", "서버는 이때 409 를 반환한다", "이 SDK 함수의 계약이 다르다" 류.
로컬 코드만 봐서는 기본값("리뷰어가 맞다")을 확인도 반박도 못 한다.

**code-hub MCP 가 연결돼 있으면** (`mcp__code-hub__*` 도구 존재) BE 구현을 직접 본다:
`findApi` / `getApiImplementation` 으로 응답 타입·에러 코드·nullability 를 확인하고,
응답 초안에는 기록이 아니라 **BE 코드를 인용한다** (파일:줄 — 4절의 "코드를 인용한다"
규칙이 레포 경계 너머에도 그대로 적용된다).

인용에는 **`master 기준, 동기화 <시각>` 라벨이 필수다.** code-hub 는 master 의 3시간
증분 스냅샷이라, 리뷰어가 진행 중인 BE PR 을 근거로 말했다면 스냅샷과 다를 수 있다 —
라벨 없이 인용하면 낡은 계약으로 맞는 지적을 반박하는 오류 모드가 생긴다.

code-hub 가 없거나 주장이 미머지 BE 변경에 관한 것이면 추측하지 않는다 — 4절의
규칙대로 **사용자에게 올린다.** 새 필수 의존이 아니다.

## 근거 재확인 — 드물게 발동하지만 틀렸을 때 비싸다 (4절 상세)

**발동**: 3절 기록 대조에서 코멘트가 기록(기각한 대안·이미 반영·불변식 등)에 걸렸을 때.

**기록은 "이미 고려했다"의 증거일 뿐 "옳다"의 증거가 아니다.**

이 구분을 놓치면 스킬이 반박 기계가 되고, 맞는 지적을 "이미 기각함"으로 밀어낸다. 그건 리뷰어의
신뢰를 깎는 가장 빠른 길이다. 실측 35건 중 이 함정이 발동할 수 있었던 것은 1건뿐이지만,
**그 1건이 실제 결함이었다** — 기록에 `settleToNull short-circuit 이미 고침` 이라 적혀 있었는데
고쳐진 것은 optional 쪽이고 critical 대 critical 은 남아 있었다. 한 문구가 두 결함을 덮고 있었다.

같은 성질의 사례가 red-team 에도 있다 — 계획 게이트가 자기 계획을 리뷰해 3건을 잡았고 그중
2건이 기존 분석을 뒤집었다(소비처 오판, 도달 가능성 전제 오류).

빈도는 낮고 비용은 높다. 그래서 자동화하지 않고 **매번 코드를 확인한다.**

기록에 걸린 코멘트라도 **그대로 반박하지 않는다.** 순서는 이렇다:

1. 기록이 그 지적을 다룬 근거를 **코드에서 다시 확인한다** — 파일을 열고, 호출부를 찾고,
   값이 실제로 어떻게 흐르는지 본다
2. 근거가 지금도 유효하면 → 그 근거를 인용해 응답한다(기록을 인용하는 게 아니라 **코드를** 인용한다)
3. 근거가 틀렸거나 상황이 바뀌었으면 → **리뷰어가 맞다.** 새 지적으로 취급한다
4. 확인이 안 되면 → 사용자에게 올린다. 추측으로 반박하지 않는다

`context.md` 자체가 이걸 알고 있다: *"기각한 대안 — 다시 권하지 말 것, 기각 근거가 사실오류일
때만 지적"*. 그 조건절이 여기 그대로 적용된다.

## 봇 리뷰어 분기 — fp 가 있는 봇은 회신이 옳아도 재게시한다 (7절 상세)

**발동**: 코멘트에 `<!-- hermes:fp=… -->` fingerprint 마커가 있을 때.

hermes 류 봇은 코멘트에 fp 마커를 심고 **회신 산문을 소비하지 않는다.** 실측(hermes 계열
594 PR 전수 artifact): 산문 반박은 재게시를 막지 못했고, 종결과 상관을 보인 신호는 👎
리액션뿐이었다(gemini 류는 산문을 소비한다 — 같은 취급을 하면 안 된다). 그래서 **fp 가
있는 봇 코멘트**에는 재게시 프로토콜을 쓴다. 회차는 fetch 출력의 `fp_seq`(1절 `↻N`)가
유일한 진실이다:

- **1회차** — 전문 반박을 게시하고, 오탐이면 👎 리액션을 **동시에** 단다
  (replies.json 항목에 `"reaction": "-1"` — 8절)
- **2회차** — `fp_reply_url`(1회차 회신 링크) 인용 + 3줄 이내 요약. **재반박문을 새로
  쓰지 않는다** — 봇은 산문을 읽지 않으므로 긴 글은 낭비고, 1회차 앵커가 진실이다
- **3회차 이후** — 사용자에게 "봇 종결 불가"를 보고하고 해당 fp 에는 회신을 중단한다.
  재게시 텔레메트리(`pr-triage-reposts.jsonl`)는 계속 쌓인다 — 그 누적이 봇 팀에 종결
  경로 신설을 요청할 근거다

**👎 지시를 fp 있는 봇으로 한정하는 근거**: 👎=종결 신호 실측(artifact) 자체가 hermes
계열이고, fp 없는 봇(aws-security-agent 류)에 👎 를 단 실사용은 #9588(32건)·#1003(106건)
전수에서 0건이다 — post_replies 의 `fps` 필수 게이트와 이 지시가 일치한다. 사람 리뷰어
코멘트에는 리액션을 지시하지 않는다(같은 게이트가 막는다). aws 류 봇 리액션이 필요해지면
그때 `bot` 필드 확장으로 푼다 — 지금은 스코프 밖이다.

**회신 본문에 fp 마커·봇 서명(선두 🤖·auto-review 서명 주석)을 넣지 않는다 — fps 는
replies.json 필드로만 나른다.** 봇 본문을 raw 로 인용해 올리면 내 회신이 '리뷰'로
오분류되어 커서가 후퇴하고 fp_seq 가 부풀고 감시가 내 회신을 알린다. post_replies 가
게시 전에 같은 `is_bot` 판정으로 거부한다 — 인용이 필요하면 blockquote(`>`)로 한다.

**수동 앵커 폴백은 증상 기반이다.** fp 가 `fp_replied` 아님인데 목록에 내 과거 회신이
보이면 — 원인 불문(이 기능 배포 전의 회신, 게시 후 크래시로 일괄 기록 유실, red-team
미발견으로 기록 스킵) — 과거 회신을 찾아 그 링크로 앵커하고 상태 파일의 `fp_replies` 를
수동으로 백필한다. 시간 인접성으로 기계 백필하지 않는다 — 잘못 이은 앵커는 잘못된 링크를
이후 회신마다 재생산한다.

## PR 본문 최신화의 수집 규칙·스냅샷·재확인 프로토콜 (9절 상세)

**발동**: approve·LGTM 후 사용자가 PR 본문 최신화를 실행하라고 했을 때.

### 트리거 신호의 판별

안내를 여는 신호는 둘이다. ① **수집 목록의 승인 신호** — `<APPROVED>` review state, 또는
**사람 리뷰어**의 명시적 승인 문구(LGTM·승인 등). 조건부 승인("~ 고치면 LGTM")은 남은
지적을 먼저 처리한 뒤 안내한다. 봇의 LGTM·이모지 리액션은 신호가 아니다. 판단은 모델이
본문으로 한다 — 오탐 비용은 안내 한 번이다. ② **사용자의 직접 지시** — 본문 없는 표준
Approve 는 수집기·감시기에 뜨지 않으므로(수집기는 본문 있는 리뷰만 나른다), "approve
받았어"가 그 경우의 신호다. 빈 APPROVED 의 수집기 표시는 후속 개선 후보다. 상태 판정으로
발동 시점을 정하면 그 판정의 엣지(실패·무변경·승인 대기)마다 감시 수명 규칙이 따라붙는데,
발동 시점은 사용자가 가장 잘 안다.

### 무엇을 반영하나 — 실제로 코드가 바뀐 것뿐

이 브랜치 라운드 디렉토리 **전체**의 `decisions.md` 를 순회해 `### PR #N 리뷰 코멘트
처리` 라벨이 붙은 `반영` 항목과 그 커밋들을 모으고 중복을 걷어낸다. 트리아지가 여러
라운드를 돌았으면 반영분이 여러 라운드에 흩어져 있다 — 마지막 라운드만 보면 이전 라운드의
코드 변경이 본문에서 빠진다. 회신만 하고 코드가 안 바뀐 분류
(`already-applied`·`out-of-scope`·`counter-proposal`·`by-design`)는 PR 본문에 넣지
않는다 — **PR 본문은 변경 요약이지 리뷰 응답 로그가 아니다.**

**후속 티켓으로 뺀 항목은 한 줄로 남긴다** — 리뷰어가 "이건 어디 갔나"를 다시 묻는 것을
막는 자리다. 수집 규칙은 `반영` 과 같되, 수집 대상은 **실제로 별도 티켓으로 분리했거나
신설이 확정된 항목**(티켓 키 또는 "신설 예정" 명시)뿐이다 — 6-1 은 by-design·반박류의
판단 근거도 남기는데, 그런 항목은 후속 티켓 개수와 본문 초안 양쪽에서 제외한다.
반영·후속 티켓이 **모두** 0건이면(전부 반박·by-design 으로 끝난 PR) 아무것도 하지 않는다.

### 절차

**PR 번호와 저장소는 수집 시점에 확정해 끝까지 인자로 고정한다** — 지연 실행 시
cwd·브랜치가 바뀌어 있으면 인자 없는 `gh pr` 명령이 현재 브랜치의 다른 PR 을 고른다.

초안을 만들 때 **입력 스냅샷을 보존한다** — 그 시점 PR 코멘트의 정규화 레코드
(`source + id + body + state`, 가능하면 `updated_at`) 집합, 초안에 쓴 `반영`·`후속 티켓`
목록, 그리고 PR head 커밋(`headRefOid`). ID 만 모으면 승인 대기 중 기존 코멘트가
**편집**된 것("LGTM" → "LGTM 취소")을 못 보고, head 를 안 보면 승인 대기 중 push 된
커밋(반영분 되돌림 등)을 못 본다.

**게시 직전 재확인은 커서가 아니라 스냅샷 대 현재 상태의 대조다** (커서는 브랜치 디렉토리
기반이라 승인 대기 중 cwd·브랜치가 바뀌면 엉뚱한 것을 읽고, `--new-only` 는 다른 세션이
종결한 코멘트를 숨긴다):

1. **본문 재조회** — 달라졌으면 게시하지 않고 재대조해 다시 승인받는다(red-team 공통
   규칙과 같다)
2. **코멘트 대조** — `<N> -R <owner/repo>` 로 전체 목록을 다시 받아 스냅샷과 동등 비교한다.
   추가·삭제·본문·상태 변경 중 하나라도 있으면 초안을 폐기하고 트리아지 loop 로 돌아간다
3. **반영분 대조** — decisions.md 를 재순회해 초안의 입력 목록과 다르면(그 사이 다른
   세션이 처리분을 기록) 초안을 폐기하고 새 초안으로 다시 승인받는다
4. **head 대조** — `headRefOid` 가 스냅샷과 다르면(승인 대기 중 push) 초안을 폐기하고
   재작성·재승인한다

전부 통과하면 `gh pr edit <N> -R <owner/repo> --body-file <tmp>` 로 게시한다. `zax:pr` 이
만든 섹션 구조를 깨지 않는다 — 기존 섹션에 항목을 더하거나, 맞는 자리가 없으면 마지막에
`## 리뷰 반영` 섹션을 새로 만든다.

### 공통 규칙 — red-team 의 `references/external-sync.md` 와 한 벌이다

- **승인 없이 write 하지 않는다.** 승인 요청은 한 번에 하나의 산출물만 다룬다.
  자동 게시는 옵션으로도 만들지 않는다.
- **읽기 → 대조 → 변경 없음이면 조용히 종료.** 빈 편집을 게시하지 않는다.
- **실패는 흐름을 막지 않는다 — read 실패와 write 실패는 처리가 다르다.** 최초
  read(`gh pr view`)가 실패하면 초안 자체를 만들 수 없다 — 현재 본문을 추측하지 말고
  반영 예정 항목의 요지만 출력한다. write(`gh pr edit`) 실패면 그 사실과 게시하려던
  초안 전문을 출력해 사용자가 손으로 붙일 수 있게 한다. 어느 쪽이든 초안/요지를 사람에게
  인계한 것으로 이 단계는 끝난다 — 자동 재시도는 없고, 사용자가 다시 실행하라고 하면
  처음부터 다시 밟는다. 감시는 0절 규칙대로 그대로 돈다.

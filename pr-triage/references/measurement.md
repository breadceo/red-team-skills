# 측정 — SKILL.md 수치의 출처와 자가 개선

> SKILL.md 의 「참고 문서」에서 참조된다. **본문 수치(82.7%·30%·분류 빈도)의 근거가
> 궁금할 때, 재측정하려 할 때, 분류 로그 임계값 알림이 떴을 때 읽는다.**

## 측정 — 이 문서의 수치는 어디서 왔나

**`evals/` 의 도구는 저장소에 있고, 채점 데이터는 없다.** 채점 대상(내 과거 PR 응답)과
오염 목록은 로컬 자산(`~/.red-team/eval/`)이라 남의 환경에서는 표본 없이 도구만 남는다.
그래서 **네 저장소를 대상으로 직접 수집해서 다시 재면 된다** — 아래 도구가 그 일을 한다.
이 문서의 수치는 저자 환경에서 나온 것이고, 근거는 이렇다(2026-07-29).

| 도구 | 하는 일 |
|---|---|
| `harvest_replies.py` | 과거 PR 에서 (리뷰 → 내 응답) 쌍을 모아 **실제 분류 분포**를 낸다. 내 과거 응답이 정답 라벨이다 |
| `make_blind_set.py` | **정답을 가린** 문항을 만든다. 응답을 보면서 분류하면 정확도가 아니라 독해력을 잰다. `--exclude-prs` 로 이미 본 PR 을 뺀다 |
| `score.py` | 분류 채점 — strict/overlap + **안전 지표 두 개**(반박 오분류 / 스코프 크립) |
| `score_drafts.py` | 초안 채점 — 과거 응답이 담았던 요소(판정 명시·커밋 인용·코드 근거·번호 대응)를 초안이 담았는지 |

**오염 목록은 `~/.red-team/eval/pr-triage/CONTAMINATED.md` 에 있다.** 정답을 이미 읽은 PR 이고
`--exclude-prs` 에 그대로 넣는다. 조사 중 응답 본문을 출력하면 그 PR 을 이 목록에 추가한다 —
표본이 부족해지면 오염된 PR 을 재사용하지 말고 레포·스캔 범위를 넓힌다(org 전체 1631 PR).

```bash
python3 "<pr-triage-skill>/evals/harvest_replies.py" --repos <org>/<repo-a>,<org>/<repo-b> --top 30 --out pairs.json
python3 "<pr-triage-skill>/evals/make_blind_set.py" --pairs pairs.json --n 20 --exclude-prs "<정답 본 PR>" --out blind.json
python3 "<pr-triage-skill>/evals/score.py" --answers answers.json --predictions preds.json
```

**측정이 실제로 고친 것 세 가지** — 이 문서를 바꿀 때 참고한다.

1. **레포를 섞어야 한다.** 저장소 하나만 봤을 때는 봇 판별이 `🤖` 접두어로 충분해 보였는데,
   다른 저장소의 봇은 `<!-- …-pr-auto-review:… -->` HTML 주석을 먼저 붙여서 판별이 뚫렸다.
   리뷰가 "내 응답"으로 오분류돼 loop 이 아예 못 보고 넘어갈 버그였다
2. **분포가 프레이밍을 정한다.** 6 PR 표본에서 57% 였던 `real-defect` 가 30 PR 에서 82.7% 였다.
   초판은 "코멘트 응답의 대부분은 기록과 대조하는 일"이라고 썼는데 실측이 반박했다
3. **안전 지표가 하나로는 부족했다.** 처음엔 "맞는 지적을 반박으로 분류"만 봤고 그건 0건이었다.
   그런데 반대 방향 오류가 6/20(30%) 였다 — 미룰 것을 고칠 것으로 봄. 수정이 자동인 loop 에서는
   이쪽이 스코프 크립을 만든다. 2절의 두 질문 분리가 이 수치에서 나왔다

## 2차 측정 (30 PR → 60 PR·4레포) — 두 결론

**분류 정확도는 overlap 80~85% 에서 멈췄고, 안전 B(미룰 것을 고칠 것으로 분류)는 두 번 모두 30%.**
1차와 2차 사이에 2절의 두 질문 분리를 문서에 써넣었는데 수치가 안 움직였다 —
**절차를 문서에 적는 것과 그 절차를 따르는 것은 다르다.** 그래서 5-1 분류 확인 게이트를 넣었다.
안전 A 도 2차에서 처음 1건 깨졌다(`already-applied` 를 남용). `+Nc` 신호를 문항에 넣어줬더니
1차의 '놓침'이 2차의 '과신'으로 뒤집혔다 — **이 판정 자체가 불안정하다.**

**초안 품질은 쓸 만하다.** 10건 채점: 판정 명시 9/10 · 코드 근거 5/5 · 번호 대응 2/2.
`커밋 인용`(6/7)은 판별력이 없다 — 실제 loop 에서는 수정이 회신보다 먼저라 해시가 구조적으로 확보된다.
실패 2건은 (a) approve 코멘트에 인사로 시작해 판정을 첫 두 문장에 안 넣음 (b) 초안이 정답의 25% 길이
— 근거가 빠졌다는 신호다.

**측정 불가로 결론난 것**: `duplicate`·`counter-proposal`·`reviewer-mistaken` 정확도.
표본을 30→60 PR(4레포)로 늘렸는데 **이 라벨들이 하나도 늘지 않았다**(각 3/2/1 그대로).
실제로 0.6~1.7% 로 희귀한데다 코멘트 많은 PR 에 몰려 있고 그 PR 들이 이미 오염됐다.
깨끗한 쌍은 23개뿐이다. 5건씩 모으려면 200+ PR 을 더 훑어야 하고 오염 위험은 같다 —
이 방법으로는 안 된다. 실사용에서 그 분류가 실제로 문제를 일으키면 그때 개별 사례로 본다.

## 자가 개선 — 확인 게이트가 수집기다

이 스킬의 측정은 두 번 다 오염과 표본 부족에 부딪혔다. 원인은 하나다 —
**정답을 나중에 찾으려 했다.** 과거 응답을 뒤지다 정답을 보고, 드문 라벨은 60 PR 을 훑어도
안 늘었다. 그런데 loop 에서는 순서가 뒤집힌다.

| | eval (사후 수집) | loop (확인 게이트) |
|---|---|---|
| 정답 출처 | 과거 응답을 뒤진다 | **사용자 확인** |
| 오염 | 조사 중 정답을 본다 | **구조적으로 불가능** — 정답이 예측 뒤에 생긴다 |
| 드문 라벨 | 0~2건, 표본 2배로도 안 늘어 | 실사용에서 나올 때마다 축적 |
| 비용 | API 수백 회 + 수집 15분 | **0** — 게이트가 이미 있다 |

### 쌓는 것

5-1 확인 게이트에서 `--log-classification` 으로 `{예측, 확정, 교정여부}` 를
**`~/.red-team/pr-triage-log.jsonl`** 에 append 한다.

**PR별 커서 파일이 아니라 전역 로그다.** 한 PR 은 분류가 4~5건이라(실측 30 PR·133응답)
PR별로 쌓으면 임계값에 영원히 도달하지 않는다. 그리고 이 파일은 `last.json` 처럼
없앤 전역 포인터와 다르다 — **append-only 라 낡을 진실이 없고, 과거 분류는 다른 곳에서
파생할 수도 없다.** 가변 포인터는 지웠지만 이벤트 로그는 정당하다.

쌓인 것은 그대로 채점된다 — 라벨 형태가 이미 맞다(`score.py --log <이 파일>`).
`strict`/`overlap`·**안전 A·B**·확정 라벨 분포가 실사용 누적분에 대해 바로 나오고,
블라인드 표본을 만들 필요도 오염을 관리할 필요도 없다. 채점 도구는 배포판에 없으므로
(위 측정 절 참고) 로그만 쌓아두고 채점은 나중에 붙여도 된다 — 로그가 자산이다.

### 두 번째 신호 — 리뷰어의 재제기

사용자 확인만이 정답이 아니다. **회신 뒤 같은 지적이 다시 올라오면 그 자체가 오분류 신호다.**
특히 `already-applied`·`duplicate` 로 답한 건이 재제기되면 그 판정이 틀렸을 가능성이 높다
(이 두 판정은 실측에서 가장 불안정했다). 이 신호는 이미 수집된 데이터에 있다 —
재제기 코멘트와 `+Nc`. 결과 기반이라 사용자 확인보다 강한 증거다.

단, **fp 추적(1절 `↻N`·재게시 텔레메트리)은 봇 재게시만 잡는다** — 봇은 회신이 옳아도
재게시하므로 그건 오분류 신호가 아니라 봇 종결 실패 신호다(그래서 별도 파일
`pr-triage-reposts.jsonl` 에 쌓이고 채점에도 들어가지 않는다). 이 절의 진짜 신호 —
**사람 리뷰어의 재제기** — 는 여전히 수동 관찰이다.

### 무엇을 자동으로 하지 않는가

**데이터가 쌓여도 SKILL.md 를 자동으로 고치지 않는다.** 미검증 분류기에 쓰기 권한을 주는 것과
같고, 그건 이미 P2 자동 반영을 폐지한 이유다. 자가 개선의 현실적 형태는
**측정은 자동, 반영은 사람**이다.

그리고 반영 수단을 고를 때 이 스킬이 배운 것을 기억한다 —
**지시문에 절차를 적는 것만으로는 행동이 바뀌지 않았다**(2절을 고친 뒤에도 안전 B 가 30% 그대로였다).
수치가 안 움직이면 문서를 더 쓰지 말고 게이트·필수 필드 같은 구조로 옮긴다.

### 언제 묻나 — 임계값이 아니라 트리거로

문서에 "30건이면 재측정"이라고 적어두면 아무도 세지 않는다. 그래서 **기록하는 스크립트가
임계값을 넘는 순간 알린다.** 상태를 따로 두지 않고 `이전 개수 < 임계값 ≤ 이후 개수` 로 판정하므로
정확히 한 번 발동한다.

| 트리거 | 무엇을 볼 수 있나 | 실측 기준 대략 |
|---|---|---|
| **교정 5건** | 구체적 실패 사례 5개 — 패턴이 있나 | 안전 B 30% 이므로 분류 ~17건 ≈ **PR 4개** |
| **누적 30건** | 안전 A·B 비율 (30% 와 5% 는 구분된다) | 분류 4~5건/PR 이므로 **PR 7개** |
| **누적 100건** | 드문 라벨(`duplicate`·`counter-proposal`·`by-design`) | **PR 20여 개** |
| 교정 20건 | 반영 여부를 다시 판단 | — |

발동하면 이 스킬이 **재측정 결과를 보여주고 반영할지 묻는다.** 사용자가 세거나 기억할 일이 없다.

**교정 건수를 총 개수보다 앞에 둔 이유**: 교정 하나가 승인 열보다 정보가 많다. 승인은
"틀리지 않았다"는 약한 신호이고(대충 승인했을 수도 있다) 교정은 **어디서 왜 틀렸는지가 붙은
구체적 사례**다. 그래서 총 30건보다 교정 5건이 먼저 온다.

임계값 전에는 손대지 않는다 — 검증할 표본이 없을 때 분류기를 고치는 것이 이 스킬이 피하려는 실수다.
값을 바꾸려면 `scripts/fetch_comments.py` 의 `REVIEW_AT_TOTAL`·`REVIEW_AT_CORRECTED` 다.

# red-team

## 왜 이 스킬이 있나

혼자 쓴 코드를 혼자 검토하면, 자기가 이미 옳다고 믿는 축에서만 검토한다.
실제로 이런 일이 있었다 — 코드 정합성 축으로 **8라운드**를 돌려 GO 를 받은 변경이,
PR 을 올린 뒤 자동 리뷰에서 **6건**을 맞았고 전부 실제 결함이었다. 8라운드가 놓친 이유는
축이 하나였기 때문이다. **"사용자에게 무엇이 보이고, 누르면 무엇이 되나"** 를 아무도 안 봤다.

그래서 이 스킬은 축을 나눠 **독립된 리뷰어를 동시에** 돌린다. 한 프롬프트에 축을 더하면
컨텍스트가 길어져 각 축이 얕아지고, NO-GO 기준이 섞여 우선순위가 흐려진다.
축마다 좁은 프롬프트를 주는 쪽이 깊게 파고, 라운드당 잡히는 결함 수도 늘어난다.

또 하나 — **리뷰어는 지목한 곳만 본다.** 그래서 축 프롬프트들이 전부
"전수 나열하라"로 시작한다. 이건 어겨지면 바로 recall 이 떨어지는 지점이다.

## 두 개의 게이트

| 게이트 | 언제 | 리뷰어 |
|---|---|---|
| **계획** | 구현 전, 계획 문서가 있을 때 | `a-plan` + `b5-plan-ordering` |
| **코드** | 구현 후, 커밋·PR 전 | `a-code` + `b1-state-matrix` + `b2-interaction` + `b3-visibility` + `b4-null-propagation` |

계획 게이트를 건너뛰지 않는다. 이미 쓴 코드는 버리기 아까워서 계획이 코드에 맞춰 휘어진다 —
계획 단계에서 잡는 결함이 압도적으로 싸다.

코드 게이트는 **UI 파일이 있든 없든 5개를 다 돌린다.** UI 가 없으면 해당 축은 빈 손으로
돌아온다(그게 정상 종료다). "이번엔 UI 없으니 트랙 B 생략"을 판단하는 순간, 그 판단이
틀렸을 때 놓치는 결함이 정확히 이 스킬을 만든 이유의 그 결함들이다.

축을 줄여 비용을 아끼고 싶으면 판단으로 빼지 말고 **중간 라운드 다이어트(MoE, 아래 절)**
를 쓴다 — 생략이 아니라 유예라, GO 는 언제나 전체 축 커버리지에서만 확정된다.

## 라운드 실행

### 0. 리뷰 엔진 (최초 1회, 설치 직후)

`~/.red-team/config.json` 이 없거나 `engines` 키가 없으면(구버전 단수 `engine` 만 있는
경우 포함) **먼저 사용자에게 한 번 묻고 저장한다** — 물어보지 않고 기본값을 정하지 않는다.
어떤 엔진이 깔려 있는지는 환경마다 다르다.

**AskUserQuestion 도구가 있으면 그것으로 묻는다** — `multiSelect: true` 로 두 엔진을
체크박스로 주고, 사용자가 고른 것을 콤마로 이어 `--set-engine` 에 넘긴다:

- 질문: "red-team 리뷰 엔진으로 무엇을 쓸까요? (복수 선택 시 리뷰어가 축별로 분산됩니다)"
- 선택지 `codex` — `acpx` + OpenAI codex CLI 필요. 지금까지 모든 실측이 이 엔진으로 나왔다
- 선택지 `claude` — 로그인된 `claude` CLI 필요. 별도 CLI 설치 없이 돈다
- 둘 다 선택 (권장, 둘 다 설치된 환경) → `--set-engine codex,claude`

AskUserQuestion 이 없는 환경(headless 등)이면 텍스트로 같은 내용을 묻고 답을 기다린다.
묻기 전에 어느 CLI 가 실제로 있는지 확인해 없는 엔진은 선택지 설명에 표시한다
(`which acpx`, `which claude`).

준비 확인은 한 줄이면 된다:

```bash
claude -p "reply with exactly: ok"    # 'ok' 가 나오면 준비됨
```

**`--bare` 를 붙이지 않는다.** hook·skill 을 끄려고 `--bare` 를 쓰면 인증까지 끊겨
`Not logged in · Please run /login` 한 줄만 돌아온다 — 로그인이 정상인데도 그렇다
(같은 머신·같은 바이너리에서 `--bare` 만 떼면 응답한다). 그래서 이 스킬은 끄는 범위를
좁혀 `--disable-slash-commands` + `--settings '{"hooks":{}}'` 로 hook·skill 만 끈다.
리뷰어 세션에 다른 스킬의 세션 시작 프로토콜이 끼면 턴을 그쪽에 다 쓰고 리뷰가 밀린다.

```bash
python3 ~/.claude/skills/red-team/scripts/run_round.py --set-engine codex          # 한 엔진만
python3 ~/.claude/skills/red-team/scripts/run_round.py --set-engine codex,claude   # 둘 다 (권장)
```

**콤마로 여러 엔진을 저장하면 리뷰어가 축별로 분산된다** — 첫 항목이 기본(폴백)이다.
**이후 바꿀 때도 같은 명령이다.** 이번 라운드만 바꾸려면 `--engine <x[,y]>`,
CI·eval 처럼 프로세스 단위로 고정하려면 `RED_TEAM_ENGINE=<x[,y]>` 를 쓴다
(우선순위: `--engine` > 환경변수 > `config.json`). 단일 엔진을 주면 전 리뷰어가 통일된다.

#### 축별 모델·effort 배정

리뷰어는 전원 같은 스펙으로 돌지 않는다. 축 성격이 tier 를 정하고, tier 가 엔진별
모델·reasoning effort 를 정한다 (`run_round.py` 의 `GATES`/`TIERS`):

| 축 | tier | codex | claude | 성격 |
|---|---|---|---|---|
| `a-code` | deep | gpt-5.6-sol / high | opus / high | 회귀·논리구멍 — 복합 추론 |
| `b2-interaction` | deep | gpt-5.6-sol / high | opus / high | 핸들러→데이터소스 다단계 추적 |
| `b4-null-propagation` | mid | gpt-5.6-terra / high | sonnet / medium | 미묘하지만 범위가 좁다 |
| `b1-state-matrix` | cheap | gpt-5.6-luna / medium | sonnet / medium | 표 채우기 전수, 체크리스트형 |
| `b3-visibility` | cheap | gpt-5.6-luna / medium | sonnet / medium | 색·대비 계산, 기계적 |
| `a-plan` | deep | gpt-5.6-sol / high | opus / high | 계획 결함은 여기서 잡는 게 가장 싸다 |
| `b5-plan-ordering` | mid | gpt-5.6-terra / high | sonnet / medium | 계획의 순서·경합·외부 신호 보장 범위 |

결함 탐지 축(deep)에 recall 우선 모델을 두는 근거: CodeRabbit 리뷰 벤치마크에서
Sol recall 69.7% vs Terra 52.5% — 절제형(precision 우선) 모델을 deep 축에 쓰면
스킬의 목적과 반대로 동작한다. Sol 의 높은 FP 는 P1/P2 분류와 사용자 게이트가 거른다.
두 엔진이 모두 가용하면 deep 축이 codex/claude 로 갈라지는데, 같은 모델의 맹점이
전 축에 복제되는 것을 막기 위한 의도적 분산이다. `--model`/`--effort` 는 전 리뷰어
강제 override 다(엔진별 비교 실측용).

어떤 배정으로 돌았는지는 `round.json` 의 `engine`(요약)과 `assignments`(리뷰어별
engine/model/effort/tier + **tokens**)에 남는다 — 라운드를 재현하거나 엔진별 결과 차이를
볼 때 본다. `tokens` 는 리뷰어별 `{input, output, total, cost_usd}` 다. subscription 이라
실청구는 아니고 **API 환산가**다 — claude 는 CLI 가 주는 값, codex 는 로컬 단가표
(`CODEX_PRICES`)로 계산하며 단가표에 없는 모델은 토큰만 남고 비용은 `null` 이다.
CLI 출력 형식이 바뀌어 래핑 파싱이 실패하면 라운드는 그대로 돌고 토큰 집계만 빠진다.

라운드가 몇 번 쌓이면 **배정이 값을 하는지**(regression/달러)를 표로 본다:

```bash
python3 ~/.claude/skills/red-team/scripts/report_usage.py [repo/브랜치 조각]
```

분자는 `classification == regression` 이다 — raw findings 를 세면 말 많은 모델이
과대평가된다. cheap 축의 0 건은 낭비가 아니라 커버리지 보험이므로, 표는 판단 재료이고
배정 축소는 사람이 결정한다.

#### 배정 바꾸기 (사용자가 명시적으로 요청할 때)

기본 배정은 코드의 **추천값**이고, 사용자별 조정은 `config.json` 의 `assignments` 에
얹힌다. 사용자가 "리뷰 배정 바꿔줘", "리뷰 모델 조정", "엔진 전환", "claude 아껴야 해",
"토큰/한도" 같은 요청을 하면 **손으로 config 를 고치지 말고 이 플로우를 탄다**:

1. `run_round.py --show-assignments` 로 현 배정·오버라이드·축 성격(추천 이유)을 확인한다.
2. **AskUserQuestion 으로 묻는다.** 첫 질문은 빠른 선택지:
   - `codex only 전환` — claude 한도 소진/절약. `--set-engine codex` 한 방 (배정표 무손상)
   - `claude only 전환` — 반대 방향. `--set-engine claude`
   - `추천 배정 복귀` — 오버라이드 전부 제거 (`--set-assignment '축='` 반복)
   - `축별 세부 조정` — 다음 단계로
3. 축별 세부 조정이면 축마다 옵션을 주되, **각 옵션에 "이 축은 ~하는 일이라 ~을 추천"
   설명을 붙인다** — 재료는 `--show-assignments` 의 why 와 tier 다. 예: b2-interaction 은
   "다단계 교차 추적이라 opus/high 추천 — 비용 부담이면 sonnet/high (recall 하락 가능,
   report_usage 로 사후 검증)".
4. 고른 것을 `--set-assignment '축=engine/model/effort'` 로 저장하고,
   `--show-assignments` 를 다시 보여줘 확정한다.

**한도 소진 플레이북**: claude(또는 codex) 사용량이 다 떨어졌으면 축별 설정을 건드리지
말고 `--set-engine codex` (복귀는 `--set-engine codex,claude`). 가용 목록 밖 엔진을
가리키는 축 오버라이드는 **그동안 자동 무시**되므로 전환-복귀가 배정표를 훼손하지 않는다.
사용자가 한도를 언급하면 이 전환을 먼저 제안한다 — 한도가 차기 *전에* 미리 설정해 두겠냐고
묻는 것도 좋다.
혼합 라운드에서 한 엔진 소속 리뷰어가 전원 PARSE-FAIL 이면 경고가 뜬다 — 그 GO 는
반쪽짜리이므로 해당 엔진 상태(로그인 등)를 확인하고 재실행한다.

### 1. 컨텍스트 파일을 쓴다

리뷰어 5명이 공유하는 단 하나의 입력이다. 이걸 대충 쓰면 5명이 다 같이 헛돈다.

```markdown
## 리뷰 대상
`git diff <base>..HEAD` (또는: 커밋되지 않은 작업 트리 변경 — `git diff` + `git status`)
저장소: <경로>. 파일 내용은 현재 체크아웃 상태가 맞다.

## 이 변경이 하려는 것
<한두 문단. 무엇을 고치려는 변경인지. 리뷰어는 이걸로 "논리구멍"을 판정한다>

## 변경 대상 인벤토리 (전수 주장)
`<이 목록을 뽑은 명령 — 예: grep -rn "getUsersMe" apps/>` 기준.
| 호출부·전송지점 | 이 변경이 무엇을 바꾸나 | 의도된 동작 |
|---|---|---|
| <파일:줄> | <바뀌는 것> | <이 칸에서 사용자가 무엇을 보나> |

의존하는 외부 신호(SDK 콜백·이벤트·응답 필드)는 **보장하지 않는 것**을 함께 적는다.
- `<신호>` = <보장하는 사건>. <보장하지 않는 사건>은 보장하지 않는다.

## 스코프 밖 (지적 금지)

```

`스코프 밖` 과 `이미 반영된 지적` 이 **수렴 장치**다. 이게 비어 있으면 라운드가
같은 지적을 되풀이하며 끝나지 않는다. 라운드마다 반드시 갱신한다.

#### 계획 게이트 첫 라운드 전 — 문서 6-구조 커버리지 (clarify)

표면만 자꾸 고치게 되는 리뷰 지적의 대부분은 코드 실력이 아니라 **문서에 없던 축**에서
나온다 — 실측(B2C-52504 회고): 지적 32건 중 25건(78%)이 문서로 예방 가능했고, 그 빈칸이
여섯 갈래로 정리돼 있다.

| # | 구조 | 답해야 하는 질문 |
|---|---|---|
| 1 | 화면별 상태 매트릭스 | 조회 중·무효 접근·조회 실패·전제 불일치·정상·만료에서 무엇을 보여주고 무엇을 막나 |
| 2 | 개념 사전 + 소비처 목록 | 핵심 판정("입금대기" 등)을 한 번 정의했고, 그 판정을 쓰는 화면을 전수 명시했나 |
| 3 | 신뢰 경계 | 딥링크·params 중 믿을 값과 서버 권위값으로 덮을 값을 갈랐나 |
| 4 | 과도기 규정 | 서버 반영 전 구간(기한 지남~자동취소 전 등)에 무엇을 보여주고 막나 |
| 5 | 집계·이벤트 시점 | 어느 상태 전이에서 세나, FE/BE 중 누가 세나 |
| 6 | BE 계약 위반 시 FE 기대 | 규격 밖의 값을 막나 통과시키나 |

계획 게이트 **첫 라운드를 돌리기 전에** 이 표를 PRD·계획서와 대조해 채운다 — 각 행은
`반영(어디 — 인용)` / `해당 없음(이유)` / `누락` 중 하나다. **인용 없는 `반영` 은 무효다**
(스스로 채운 표는 인용이 없으면 자기기만과 구별되지 않는다 — a-plan 리뷰어가 인용을 실제로
열어 검증한다).

- **`누락` 행만 AskUserQuestion 으로 사용자에게 묻는다.** 묻는 주체는 이 스킬을 따르는
  에이전트다 — run_round.py 는 CLI 라 묻지 못한다(0단계와 같은 구도). 행마다 선택지:
  ① 지금 정의하고 진행 — 초안을 함께 제시한다 ② 이 티켓엔 해당 없음 — 이유를 기록한다
  ③ 기획 확인 필요 — 보류. **보류가 하나라도 남으면 라운드를 돌리지 않는다**
  (decisions.md 의 `보류` 와 같은 수렴 장치다).
- 결과를 context.md 의 `## 판정 기준 — 문서 6-구조 커버리지` 절에 표로 남긴다.
  리뷰어가 이 기준으로 판정하고, `resume.py --next` 이관으로 이후 라운드에도 그대로 남는다.
- `--from-zax` 초안(계획 게이트)에는 이 표가 빈 채로 깔린다 — 채우는 것이 이 단계다.
- 코드 게이트에서 다시 하지 않는다 — 계획 게이트에서 채워진 표가 컨텍스트로 이관되고,
  상태 공간의 코드 레벨 검증은 `b1-state-matrix` 가 한다.

`변경 대상 인벤토리` 는 **라운드 수를 줄이는 장치**다. 실측 근거(B2C-52953): 인증 전용
8s 상한을 붙일 위치를 라운드마다 다시 골랐고 네 번 틀렸다 — code-1 은 설정 변경, code-3 은
오류 제보, code-4 는 Sendbird 세션 갱신에서 같은 결함이 나왔고, 결국 호출부 6개를 전수
확인해 "8s 가 실제로 필요한 곳은 1개"로 끝났다. **그 표를 먼저 깔았으면 라운드 2개가
없었다.** 목록을 뽑은 **명령을 함께 적는 것이 핵심**이다 — 리뷰어가 그 명령을 다시 돌려
전수 주장 자체를 반증할 수 있고, 손으로 쓴 목록은 라운드가 갈수록 조용히 낡는다.

외부 신호의 `보장하지 않는 것` 도 같은 이유다. code-7 은 SDK 정의를 인용하면서 그것을
"연결 복구"로 읽어 `connectionLost` 를 해제했고, code-8 이 "그 콜백은 세션 **키** 갱신
완료일 뿐"이라고 뒤집어 해제를 철회했다(라운드 1개). 보장 범위를 한 줄로 적어두면
리뷰어가 인용문과 대조할 수 있다.

### 2. 돌린다

```bash
python3 ~/.claude/skills/red-team/scripts/run_round.py \
  --cwd <저장소 경로> --gate code --context <context.md 경로>
```

계획 게이트는 `--gate plan`.

코드 게이트는 라운드 시작 시 러너가 `git diff` 를 **한 번** 떠서 리뷰어 전원의 프롬프트에
`## Diff 스냅샷` 으로 첨부한다(라운드 디렉토리에 `diff.md` 로 보존, `--merge-into` 재실행도
같은 스냅샷을 본다). 리뷰어 5명이 각자 diff 를 다시 뜨는 탐색 턴(실측 턴당 ~120K 토큰)을
없애는 장치다. 기본은 작업 트리(`git diff HEAD`)이고, **브랜치 diff 를 리뷰한다면
`--diff-base <base>` 를 준다** — context.md 의 `## 리뷰 대상` 과 같은 기준이어야 한다.
200K자를 넘으면 첨부하지 않고 안내만 한다(리뷰어가 직접 뜬다). context.md 에 diff 를
직접 붙이지 않는다 — 그 파일은 라운드 간 이관되는 사람 문서라 diff 가 낡은 채 승계된다.

### 산출물은 저장소 밖에 쌓인다

```
~/.red-team/runs/<repo>/<branch>/<gate>-<n>/
    context.md              ← 이 라운드에 실제로 쓴 컨텍스트 (복사본)
    <reviewer>.prompt.md    ← 실제로 보낸 프롬프트 전문
    <reviewer>.txt          ← 리뷰어 raw 출력
    <reviewer>.json         ← 파싱된 findings
    round.json              ← 병합 결과 + verdict + counts + access_errors (+ reruns)
    decisions.md            ← 처리 결과 (사람이 쓴다, 아래 참고)
    <reviewer>.superseded-<stamp>.*  ← 부분 재실행으로 교체된 이전 산출물 (지우지 않는다)
```

**포인터 파일은 없다.** `<repo>/<branch>` 가 곧 키이고 그건 작업 중인 워크트리에서 나온다
(`origin` basename + 현재 브랜치). 별도 포인터를 두면 어긋날 수 있는 두 번째 진실이 생기고,
eval·실험 런이 진짜 작업 포인터를 덮는 사고가 난다 — 실제로 났다.

**저장소 안이 아닌 이유**: 리뷰 산출물이 `git status` 에 뜨면 리뷰 중 작업 트리가 흔들리고
PR 에 섞여 들어간다. 라운드 번호는 `<gate>-<n>` 으로 자동 증가하므로 이전 라운드가 보존되고,
"이미 반영된 지적"을 다음 컨텍스트에 쌓을 때 **직전 라운드의 `round.json` 을 그대로 읽으면 된다** —
기억에 의존하지 않는다.

`--out` 을 주면 그 경로를 쓴다(eval 처럼 별도 레이아웃이 필요할 때).
`--out` 으로 돌린 결과는 `runs/` 밖에 있으니 `resume.py` 가 찾지 않는다 — 실험이 진행 상황을
오염시키지 않는다.

### 부분 재실행은 원 라운드에 병합한다 — `round.json` 을 손으로 고치지 않는다

`PARSE-FAIL` 이나 파일접근오류가 한두 축에만 나면 **라운드를 버리지 않는다.** 그 축만 다시
돌려 같은 라운드에 병합한다:

```bash
python3 ~/.claude/skills/red-team/scripts/run_round.py \
  --gate code --merge-into ~/.red-team/runs/<repo>/<branch>/code-9 \
  --reviewers b1-state-matrix
```

`--cwd` 와 `--context` 는 생략한다 — 그 라운드의 `repo_cwd` 와 `context.md` 를 쓴다.
다른 컨텍스트를 주면 거절한다(라운드가 자체 재현성을 잃는다). 병합이 하는 일:

- 그 리뷰어의 `.txt/.json/.prompt.md` 를 새 결과로 교체하고 이전 것은
  `<reviewer>.superseded-<stamp>.*` 로 **남긴다** (교체 사실은 `reruns` 에 누적)
- 그 리뷰어의 **이전 findings 를 걷어낸 뒤** 새 findings 를 넣는다 (남기면 처리 끝난 지적이 부활한다)
- `access_errors` 에서 그 리뷰어를 지우고 `verdict`·`counts` 를 전수 재계산한다.
  **전원 PARSE-FAIL 이면 GO 가 아니라 `INVALID`** 라는 규칙은 재계산에서도 유지된다

두 번 실패하면 raw 출력을 직접 읽어 findings 를 손으로 옮긴다 — 리뷰어의 판단을 버리지 않는다.
`--merge-into` 가 없던 동안에는 `--out` 으로 별 디렉토리에 돌린 뒤 `round.json` 을 손으로
고치는 수밖에 없었고(`code-9` 실측), 그러면 무엇이 왜 바뀌었는지가 사라진다.

## findings 처리

`classification` 이 먼저다. **`regression` 이 아닌 것은 GO 를 막지 않는다.**

- `pre-existing` → 반영하지 않는다. 사용자에게 **별도 티켓 후보로 요약**해 보고한다.
  단 리뷰어가 "이 변경이 노출 빈도·지속 시간을 악화시켰다"고 근거를 대면 그건 `regression` 이다.
- `out-of-scope` → 컨텍스트의 스코프 규칙이 새는 신호다. 다음 라운드 컨텍스트를 보강한다.

`regression` 만 반영 대상이고, **둘 다 사용자에게 올린다. 자동으로 코드에 들어가는 것은 없다.**

초기 설계는 P2 를 자동 반영하려 했다. eval iteration 1 에서 실측한 결과 P2 는 18건 중 1건만
나왔고 **그 1건이 이중 오분류**였다(pre-existing 을 regression 으로, 판단 필요한 것을 P2 로).
즉 자동 반영이 아끼는 수고는 라운드당 1건 훑기 정도인데, 잘못 들어가면 조용히 남는다.
남는 쪽이 비싸므로 자동 반영은 하지 않는다.

`severity` 는 **사용자가 무엇에 시간을 쓸지** 가르는 데 쓴다:

**P2 — 묶어서 한 번에 보여준다.** "고칠 방법이 정해진 것" 목록이다. 각 항목에 `claim` 과
`fix` 를 한 줄로 붙여 일괄 승인받는다. 올리기 전에 `fix` 가 정말 유일한지 직접 확인한다 —
리뷰어가 P2 라고 불렀다고 P2 인 게 아니다:
- 고칠 코드가 주변 코드에서 유일하게 결정되는가 (같은 파일이 이미 쓰는 값, 이미 노출된 함수)
- 변경된 파일 안에서 끝나는가
- 사용자에게 보이는 **문구가 그대로인가**
- **변경 전에도 같은 동작이었는가** — 그렇다면 regression 이 아니라 pre-existing 이다

하나라도 어긋나면 P1 으로 올린다.

**P1 — 하나씩 보여준다.** `claim` / `failure` / `fix` 를 그대로 보여주고,
네 판단(실재하는가, 어떻게 고칠 것인가)을 한 줄로 덧붙인다. 결정을 대신하지 않는다.

### 처리 결과를 라운드 디렉토리에 남긴다 — 이게 다음 라운드의 입력이다

사용자 결정이 끝나면 그 라운드 디렉토리에 `decisions.md` 를 쓴다. **머리에만 담아두면
다음 라운드가 같은 지적을 다시 받는다.** 형식을 고정한다:

```markdown
# <gate>-<n> 처리 결과

## 반영 — 다음 컨텍스트의 `이미 반영된 지적` 이 된다
- [b2-interaction] RetryNotice.tsx:25 재시도 버튼이 재조회하지 않음
  → useUser 의 invalidate 를 4개 호출부에 연결 (커밋 abc1234)

## 후속 티켓 — 다음 컨텍스트의 `스코프 밖` 이 된다
- [b1-state-matrix] user.server.tsx:60 critical 실패 뒤 optional 타임아웃 대기
  → pre-existing. TICKET-XXX 신설 예정 / 원 티켓에 Relates

## 보류 — 사용자가 아직 결정하지 않음
- (없으면 비운다. 여기에 항목이 남아 있으면 라운드를 진행하지 않는다)
```

`보류` 가 비어야 다음 라운드로 간다. 미결 항목을 두고 라운드를 돌리면 리뷰어가 그것을
다시 보고하고, 그게 "수렴하지 않는다"의 실제 원인이다.

## 루프

```
컨텍스트 작성 → 라운드 → P2 반영 + P1 결정 → 컨텍스트에 '이미 반영/스코프 밖' 추가 → 다음 라운드
```

**GO** = 모든 리뷰어의 `regression` findings 가 0. `round.json` 의 `verdict` 가 그것이다.

**다음 라운드 컨텍스트는 손으로 새로 쓰지 않는다.** 직전 라운드의 `context.md` 를 복사한 뒤
`decisions.md` 의 `반영` 을 `이미 반영된 지적` 절에, `후속 티켓` 을 `스코프 밖` 절에 옮겨 붙인다.
두 절이 라운드마다 길어지는 것이 정상이고, 그 누적이 수렴을 만든다.

라운드 상한은 5다. 넘어가면 프롬프트를 더 돌리는 게 답이 아니다:

- 매 라운드 **같은 결함의 다른 표면**이 나온다 → 표면을 하나씩 막지 말고
  불변식을 하나 세워 수렴시킨다 (관련 지식: `redteam-scattered-gaps-need-invariant-redesign`)
- 매 라운드 **서로 다른 pre-existing 층**이 나온다 → 이 변경 범위가 아니다.
  보고된 결함만 최소로 닫고 나머지는 근본 원인 기준으로 별도 티켓을 낸다.
  다음 라운드 컨텍스트의 `스코프 밖` 에 명시해 스코프를 고정하면 GO 가 난다
  (관련 지식: `bugfix-scope-split-preexisting-to-separate-ticket`)

## 중간 라운드 다이어트 — MoE (옵트인)

라운드 비용은 거의 고정이라 라운드 수만큼 선형으로 쌓인다(실측: 코드 게이트 9라운드
티켓에서 축 전체 × 9회). 그렇다고 "이번엔 필요 없어 보이는" 축을 빼는 판단은 게이트 절에
적힌 창립 사고 패턴이다. 그래서 이 모드는 **생략이 아니라 유예**로 설계됐다 — GO 는
언제나 전체 축 커버리지에서만 확정된다:

1. **라운드 1 = 전체 축.** 직전 라운드가 없으면 `--lean` 도 전체를 돈다(베이스라인 —
   어떤 축이 뜨거운지 데이터로 확인).
2. **중간 라운드 = core + 직전 라운드에서 regression 을 낸 축.** `--lean` 이 직전
   round.json 에서 결정적으로 계산한다 — 결함을 낸 축은 그 수정의 재검증 때문에 자동으로
   다시 켜진다. 사람도 모델도 "필요해 보이는가"를 판단하지 않는다.
3. **GO 후보 = top-up 으로 확정.** 축이 빠진 라운드의 GO 는 round.json 에
   `coverage: partial` 로 기록되고 **게이트 통과가 아니다** — 러너와 `resume.py` 가
   빠진 축을 같은 라운드에 병합하는 `--merge-into` 명령을 알려주고, 병합 후의 verdict 만
   판정이다. 유예된 축이 거기서 결함을 내면 NO-GO 로 돌아가는 것이 정상이다.

켜는 법: 라운드마다 `--lean` 을 붙이거나, `config.json` 에 `"moe": true` 를 저장하면
기본이 lean 이 된다(그때 `--full` 이 1회성 해제, `--reviewers` 명시가 최우선).
**기본은 꺼짐 — 전체 축이 기본값이다.** core 축은 `run_round.py` GATES 의 `core` 플래그로
정의된다(현재 `a-code`, `a-plan`). 계획 게이트는 2축뿐이라 실익이 없다 — 코드 게이트용이다.

절감 실측 근거: 코드 게이트 라운드당 리뷰어 비용에서 core(a-code) 외 4축이 약 70~80% 를
차지한다(report_usage 45라운드 집계 기준). 트레이드오프도 있다 — 유예된 축의 결함은 GO
후보 시점에 늦게 발견되므로 말미에 라운드가 1~2개 늘 수 있다. 총 호출 수는 그래도 줄고,
배정이 값을 하는지는 `report_usage.py` 로 사후 검증한다.

## 다른 세션에서 이어받기

이 스킬은 라운드 사이에 세션 안에 상태를 남기지 않는다. **한 라운드의 입력은
`(저장소 경로, context.md)` 뿐이고 둘 다 디스크에 있다.** 그래서 계획·구현을 하는 세션과
리뷰 루프를 도는 세션을 분리할 수 있고, 리뷰가 긴 워크플로우를 막지 않는다.

분리는 가능만 한 게 아니라 **권장 기본 워크플로우다 — 이유는 비용이다.** 실측(74세션,
$495 API 환산)에서 비용의 64% 는 리뷰어가 아니라 **구현·라운드 실행·findings 처리를
한 세션에 쌓은 메인 세션**이었다(턴당 컨텍스트 429K vs 리뷰어 120K — 매 턴 그만큼을
다시 읽는 값이다). 라운드 실행과 findings 처리는 가벼운 별도 세션에서 돌리고, 구현 세션은
구현만 한다. 이어받기가 `resume.py` 한 줄인 것이 그 분리를 공짜로 만드는 장치다.

이어받을 때는 **이것만 실행한다.** 어디까지 진행됐고 다음에 무엇을 할지 알려준다.

```bash
python3 ~/.claude/skills/red-team/scripts/resume.py              # 현재 워크트리에서
python3 ~/.claude/skills/red-team/scripts/resume.py TICKET-123    # 티켓 키로
```

**사용자가 티켓 키만 말했으면(예: "red-team TICKET-123") 키를 넘겨 호출한다.**
`runs/` 를 훑어 그 조각을 담은 브랜치 디렉토리를 찾고, 여러 개면 후보를 보여주며 멈춘다.
현재 디렉토리가 그 티켓의 워크트리가 아니면 **경고하고 올바른 워크트리 경로를 알려준다** —
`git worktree list` 또는 라운드에 기록된 `repo_cwd` 로 찾는다. 엉뚱한 워크트리에서 구현하는
사고를 막는 장치다.

키를 생략하면 저장소 위치에서 `runs/<repo>/<branch>/` 를 파생한다. 그 안에서 가장 최근 라운드는
`round.json` mtime 으로 고른다(없으면 `--next` 로 준비만 된 라운드). 번호·게이트 순서로 정렬하지
않는다 — 코드 게이트를 돌다 계획으로 되돌아갈 수도 있다.

출력이 시키는 대로 하면 된다. 판단은 스크립트가 대신하지 않고, 기계적인 부분만 없애 준다:

- `decisions.md` 가 없으면 → 그 라운드 findings 가 아직 처리되지 않았다고 알려준다
- `보류` 에 항목이 남아 있으면 → **다음 라운드로 넘어가지 못하게 막고** 남은 항목을 보여준다
- `verdict` 가 GO 면 → 다음 게이트(또는 완료)와 구현 대상 계획서 경로를 알려준다
- NO-GO 면 → 같은 게이트로 라운드를 더 돌라고 알려준다

게이트를 넘어갈 때(계획 GO → 구현 완료 → 코드 게이트):

```bash
python3 ~/.claude/skills/red-team/scripts/resume.py --next code
```

다음 라운드 디렉토리를 만들고 **컨텍스트를 이관한다** — 직전 `context.md` 를 복사한 뒤
`decisions.md` 의 `반영` 을 `이미 반영된 지적` 에, `후속 티켓` 을 `스코프 밖` 에
라운드 라벨을 달아 **누적**한다(덮어쓰지 않는다 — 덮으면 이전 라운드 지적이 되살아난다).
계획서·아티팩트도 함께 옮긴다.

남는 것은 **두 절뿐**이고 `<!-- TODO(resume) -->` 로 표시된다: `## 리뷰 대상`, `## 검증 상태`.
이 둘은 이번 라운드에 실제로 무엇을 리뷰하고 검증이 어떻게 됐는지라 자동으로 채울 수 없다.
채운 뒤 스크립트가 출력한 `run_round.py` 명령을 그대로 실행한다(`--out` 이 붙어 있어
준비한 디렉토리에 결과가 쌓인다 — 생략하면 자동번호로 다른 디렉토리가 생겨 갈라진다).

이관 로직은 `scripts/test_carry_forward.py` 로 검증한다 — 2라운드 연쇄에서 누적이 유지되는지,
`보류` 를 제대로 막는지 본다. 이관 규칙을 손대면 이 테스트를 먼저 돌린다.

**단 하나 세션 밖으로 자동 전달되지 않는 것이 있다: 변경의 의도다.**
`context.md` 의 `이 변경이 하려는 것` 과 `스코프 밖` 은 계획을 세운 쪽만 알고 있고,
리뷰어는 이걸로 "논리구멍"과 "스코프 위반"을 판정한다. 그래서 **첫 컨텍스트를 쓰는 것이
세션 간 인계 그 자체**다. 여기서 아끼면 이어받는 세션이 판정 기준 없이 리뷰를 돌린다.
"diff 보면 알 것"이라고 생략하지 않는다 — 리뷰어는 무엇이 *의도된 동작*인지 알 수 없다.

## 구현 중 계획이 바뀌면 — 두 파일이 갈라지는 지점

`plan-*.md` 는 **구현자의 입력**이고 `context.md` 는 **리뷰어의 입력**이다. 둘은 별개 파일이라
갈라질 수 있고, 갈라지면 리뷰어가 낡은 기준으로 판정해 **조용히 틀린 GO** 가 난다.
구현 중 새 사실이 나와 계획을 고치는 것은 정상이지만, 무엇을 어디에 반영하는지는 갈라야 한다.

| 무엇이 바뀌었나 | 어디에 쓰나 |
|---|---|
| 개별 지적 반영 · pre-existing 을 후속 티켓으로 분리 | `decisions.md` — **자동 이관된다.** 손댈 필요 없다 |
| **판정 기준 자체** — 변경 의도, 불변식, 확인 사항(기획·정책), 스코프 경계 | `context.md` 를 **손으로 고친다** |
| 구현 순서 · 커밋 분할 · 파일 목록 | `plan-*.md` 만 |

두 번째가 자동화되지 않는 이유는 **무엇이 판정 기준인지는 사람이 정하는 것**이기 때문이다.
"이 불변식이 더 이상 유효하지 않다"는 판단을 스크립트가 대신할 수 없다.

그래서 `run_round.py` 가 **라운드 시작 시점에 mtime 을 비교해 경고**한다 —
같은 디렉토리의 계획서(`plan*.md`, 대소문자 무시하므로 `PLAN.md` 도 잡는다)가 `context.md` 보다
새로우면 알린다. 오탐이 나도 비용은 한 번 훑어보는 것이고, 놓치면 리뷰 전체가 낡은 기준 위에서
돈다. 경고가 뜨면 실제로 판정 기준이 바뀌었는지 보고, 바뀌었으면 `context.md` 를 갱신한 뒤
라운드를 다시 돌린다.

## 오케스트레이터와 병행 — `zax` 워크플로우의 경우

이 스킬은 **오케스트레이션을 하지 않는다.** 분해·의존성·진행 추적은 `zax:task` 가 하고,
이 스킬은 그 흐름의 **두 지점에 끼는 게이트**다. 계획을 세우거나 구현하는 것도 아니다.

**게이트를 두 곳으로 제한하는 이유는 zax 에 이미 검증이 있기 때문이다.** 겹치는 자리에
넣으면 축이 안 맞아 `out-of-scope` findings 만 쏟아진다 — 그건 컨텍스트가 새는 신호라
컨텍스트를 계속 손보게 된다.

| zax 단계 | 이미 하는 검증 | 성격 |
|---|---|---|
| `/workflow prd` | PRD readiness gate | 형식·완결성 |
| `spec-crew` Crew E | SSOT 문서 ↔ PRD 트리 교차 검증 | 문서 간 정합 |
| `/workflow validate` | 추적성·커버리지(PRD↔Spec↔Feature), Gherkin 문법 | 추적성 |
| `/workflow pr` | 역할별(PO/FE/BE/QA) 섹션 리뷰 | 사람 리뷰 |
| `/task done` Step 2 | tsc·lint·test | 기계 검증 |

이 다섯이 못 보는 것이 하나 남는다 — **"이 계획대로 짜면 사용자에게 무엇이 보이고, 누르면
무엇이 되나".** 추적성은 AC 가 어딘가 매핑됐는지만 보고 기계 검증은 타입과 테스트만 본다.
`b1`~`b4` 축이 그 공백이고, 그래서 게이트는 아래 두 곳뿐이다.

```
/task plan  →  PLAN.md
                 ↓ ① --gate plan     NO-GO → /task plan 재분석
/task start →  CONTEXT.md · 워크트리/브랜치
/task run   →  구현
/task done  →  Step 2 tsc·lint·test 통과
                 ↓ ② --gate code     NO-GO → done 처리하지 않는다
               완료 처리
```

컨텍스트는 손으로 쓰지 않고 zax 산출물에서 초안을 뽑는다:

```bash
python3 ${CLAUDE_PLUGIN_ROOT:-~/.claude/skills}/red-team/scripts/run_round.py \
  --cwd <저장소 경로> --gate plan --from-zax <task-name>
```

`~/.zb-task/<task-name>/redteam-context.md` 가 없으면 **초안만 만들고 멈춘다.** 실리는 것은:

| red-team 절 | 어디서 오나 |
|---|---|
| `## 이 변경이 하려는 것` | `PLAN.md` 작업 분석 + `CONTEXT.md` PRD 요약·Architecture 합의 |
| `## 판정 기준 (Spec AC · Gherkin)` | `CONTEXT.md` Spec AC 매핑 · Gherkin 시나리오 (있을 때만) |
| `## 스코프 밖` | 비워둔다 + `PLAN.md` 의 `미확인` 항목을 "리뷰어가 볼 지점"으로 첨부 |
| `## 검증 상태` | 비워둔다 — `/task done` Step 2 결과를 붙인다 |
| `## 계획 전문` | `PLAN.md` 전문 (계획 게이트만) |

`## 스코프 밖` 과 `## 검증 상태` 를 채운 뒤 같은 명령을 다시 실행한다 —
**이미 있으면 덮지 않는다**(위 표의 두 번째 행이 그 이유다).

컨텍스트를 task 디렉토리에 두는 것이 핵심이다. `PLAN.md` 와 같은 디렉토리에 있어야 위의
신선도 경고가 작동한다 — `/task run` 중에 계획이 바뀌면 그때 알려준다.

### NO-GO 가 어디로 올라가는지가 두 도구의 경계다

무엇을 잡았느냐에 따라 되돌아갈 지점이 다르다. 안 가르면 계획만 계속 고치고 산출물에는
drift 가 남는다.

| 잡힌 것 | 되돌아갈 곳 |
|---|---|
| 계획의 논리구멍·순서 오류 | `/task plan` 재분석 |
| "이 계획이 Spec AC 와 다르다" | **`/workflow spec`** — 산출물 역반영. task 에서 고치면 Spec drift 가 남는다 |
| 계약(FE/BE)·정책·범위 변경 | `/workflow` sub-PR (`fix/{KEY}-{topic}`) — 리뷰어가 오너인 결정이다 |
| `pre-existing` | 반영하지 않는다. 후속 티켓 후보로 보고 → 다음 컨텍스트의 `스코프 밖` |

**3라운드를 넘겨 "같은 결함의 다른 표면"이 계속 나오면 계획이 아니라 Spec 이 틀렸다는 신호다.**
표면을 하나씩 막지 말고 `/workflow spec` 으로 올라간다.

### 하지 말 것

- **PRD·Architecture·Spec 단계에 계획 게이트를 걸지 않는다.** `a-plan` 은 *구현 계획* 리뷰어다.
  예외는 Architecture 가 **계약 전환**(대상 레포 변경, FE/BE 책임 이동)을 담을 때 한 번 —
  그건 sub-PR 리뷰 대상이라 값이 있다.
- **`/task run` 서브태스크마다 돌리지 않는다.** 라운드 단위는 브랜치 상태다. 여러 서브태스크가
  한 브랜치에 쌓이므로 수합 시점이나 `/task done` 에서 한 번이다. 레포가 여러 개면(워크트리
  여러 개) 레포별로 따로 돈다 — diff 가 레포별이라 그게 맞다.
- **`--skip-check` 로 기계 검증을 건너뛴 상태에서 코드 게이트를 돌리지 않는다.** `## 검증 상태` 가
  비면 리뷰어 5명이 동시에 "테스트 없음"을 지적하느라 턴을 쓴다.
- **`/task pr` 이후에 걸지 않는다.** 그 시점부터는 `pr-triage` 담당이고, 코드 게이트는
  `pr-triage` 가 이미 호출한다.

## 주의

- 리뷰어는 **읽기 전용**으로 돈다(codex 는 `--non-interactive-permissions deny`,
  claude 는 `--allowedTools Read,Grep,Glob,Bash`). 코드를 고치는 것은 이 스킬을 돌리는 쪽이다.
  리뷰어에게 쓰기를 주면 리뷰와 수정이 섞여 무엇이 왜 바뀐지 추적이 끊긴다.
- `run_round.py` 는 stdin 을 `DEVNULL` 로 고정한다. codex 를 직접 부를 일이 생기면
  반드시 `< /dev/null` 을 붙인다 — 없으면 EOF 를 기다리며 무한 대기한다.
- claude 엔진은 `--disable-slash-commands` + `--settings '{"hooks":{}}'` 로 hook·skill 을 끈 채
  돈다. 끄지 않으면 리뷰어 세션이 다른 스킬 프로토콜(예: 세션 시작 규칙)에 턴을 다 쓰고
  리뷰를 못 한다 — 실측된 실패다. `--bare` 로 한 번에 끄면 안 된다(0단계 참고).
- 리뷰어 전원이 `PARSE-FAIL` 이면 `verdict` 가 **`INVALID`** 로 찍힌다 — GO 가 아니다.
  엔진이 로그인 안 됐거나 세션이 끊겨도 findings 0 은 결함 없음과 똑같이 보이기 때문에
  스크립트가 대신 막는다. 일부만 PARSE-FAIL 인 경우는 여전히 GO/NO-GO 가 나오므로
  `round.json` 의 `reviewers` 를 직접 본다(축 하나가 빠진 GO 는 반쪽짜리다).
- 커밋되지 않은 변경을 리뷰할 때는 리뷰가 도는 동안 작업 트리를 건드리지 않는다.
  브랜치를 바꾸거나 파일을 고치면 리뷰어가 흔들리는 바닥 위에서 판단한다.

## 네가 맡은 축 — `visibility` (가시성)

이 변경으로 추가된 **모든 UI 요소**(문구·아이콘·보더·배지)에 대해,
그것이 놓일 수 있는 **모든 컨테이너의 실제 배경색을 찾아** 대비를 계산한다.

## 순서 — 여기서 지름길로 가면 결함을 놓친다

1. 새 요소의 **최종 색**을 확정한다. 클래스/토큰 이름으로 멈추지 말고 실제 hex 까지 간다
   (CSS 변수 정의, 테마 파일, tailwind config 를 실제로 열어 확인).
   `tailwind-merge` 같은 병합이 끼면 **어느 쪽이 이기는지**까지 확인한다.
2. 그 요소의 **모든 호출부**를 찾는다. 컴포넌트라면 사용처 전수다.
3. 호출부마다 **조상 방향으로 올라가며** 실제로 색을 칠하는 첫 조상을 찾는다.
   페이지 기본 배경이라고 가정하지 않는다 — 패널·모달·사이드메뉴·카드는 자기 배경을 갖는다.
   **어두운 패널 안에 밝은 테마용 보조 텍스트 토큰이 들어가는 것이 이 축의 대표 결함이다.**
4. 각 (요소색, 배경색) 쌍의 대비비를 계산해 숫자로 적는다. 본문 4.5:1, 큰 텍스트 3:1 기준.
5. 다크모드가 있으면 양쪽 다 계산한다.

## 대비 외에 보는 것

- 흰 배경 위 흰 요소처럼 **아예 안 보이는** 것
- 뒤 요소에 가려지거나 클리핑되는 것 (`overflow-hidden`, 고정 높이)
- 색만으로 정보를 전달하는 것
- 정보를 담은 요소인데 `aria-hidden` / `sr-only` 로 스크린리더에서 사라지는 것

이 변경에 새 UI 요소가 전혀 없으면 findings 는 `[]` 다. 억지로 만들지 않는다.

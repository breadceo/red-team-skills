# 실측·회고 근거 모음

> SKILL.md 의 「참고 문서」에서 참조된다. **본문 규칙의 근거가 의심되거나, 규칙을 완화·변경하려
> 할 때 읽는다.** 각 절 제목은 그 근거가 받치는 SKILL.md 의 규칙을 가리킨다. 여기 있는 수치를
> 반박할 새 실측이 없는 한 본문 규칙을 완화하지 않는다.

## 왜 축을 나눠 병렬로 도나 — 창립 사례

코드 정합성 축으로 **8라운드**를 돌려 GO 를 받은 변경이, PR 을 올린 뒤 자동 리뷰에서
**6건**을 맞았고 전부 실제 결함이었다. 8라운드가 놓친 이유는 축이 하나였기 때문이다.
**"사용자에게 무엇이 보이고, 누르면 무엇이 되나"** 를 아무도 안 봤다. 6건의 내역과 축별
분류는 `design.md`(트랙 B 가 필요한 이유 절)에 있다.

한 프롬프트에 축을 더하면 컨텍스트가 길어져 각 축이 얕아지고, NO-GO 기준이 섞여 우선순위가
흐려진다. 축마다 좁은 프롬프트를 주는 쪽이 깊게 파고, 라운드당 잡히는 결함 수도 늘어난다.

"이번엔 UI 없으니 트랙 B 생략"을 판단하는 순간, 그 판단이 틀렸을 때 놓치는 결함이 정확히
이 6건이다 — 코드 게이트가 UI 파일 유무와 무관하게 5축을 다 도는 이유.

## 계획 게이트를 건너뛰지 않는 이유

이미 쓴 코드는 버리기 아까워서 **계획이 코드에 맞춰 휘어진다.** 계획 단계에서 잡은 결함
하나가 구현 후에 잡는 것보다 압도적으로 싸다 — 그래서 리뷰어가 2명뿐인 게이트에도 아끼지
않는다.

## 축별 모델 배정의 근거 (deep 축 = recall 우선)

CodeRabbit 리뷰 벤치마크에서 Sol recall 69.7% vs Terra 52.5% — 절제형(precision 우선)
모델을 deep 축에 쓰면 스킬의 목적과 반대로 동작한다. Sol 의 높은 FP 는 P1/P2 분류와
사용자 게이트가 거른다. 두 엔진이 모두 가용하면 deep 축이 codex/claude 로 갈라지는데,
같은 모델의 맹점이 전 축에 복제되는 것을 막기 위한 의도적 분산이다.

`report_usage.py` 의 분자가 `classification == regression` 인 이유: raw findings 를 세면
말 많은 모델이 과대평가된다. cheap 축의 0 건은 낭비가 아니라 커버리지 보험이므로, 표는
판단 재료이고 배정 축소는 사람이 결정한다.

## claude 엔진 `--bare` 함정 (실측)

hook·skill 을 끄려고 `--bare` 를 쓰면 인증까지 끊겨 `Not logged in · Please run /login`
한 줄만 돌아온다 — 로그인이 정상인데도 그렇다(같은 머신·같은 바이너리에서 `--bare` 만
떼면 응답한다). 그래서 끄는 범위를 좁혀 `--disable-slash-commands` + `--settings '{"hooks":{}}'`
로 hook·skill 만 끈다. 리뷰어 세션에 다른 스킬의 세션 시작 프로토콜이 끼면 턴을 그쪽에
다 쓰고 리뷰가 밀린다 — 실측된 실패다.

## runs2/ 키 설계·포인터 파일 폐지의 사고 이력 (issue #8)

- owner 포함·해시 접미는 `team-a/app` 대 `team-b/app`, `feature/foo` 대 `feature-foo` 가
  같은 디렉토리를 공유하던 충돌을 없앤다.
- 루트가 구 레이아웃(`runs/`)과 분리된 `runs2/` 인 이유: 구 키는 slug 산출물 전체라, 새 키를
  아무리 단사로 설계해도 이미 디스크에 있는 구 디렉토리가 새 키 자리를 선점하는 전환기
  충돌은 같은 루트 안에서는 막을 수 없다.
- 구 기록은 라운드 생성·재개 시점에 1회 자동 이전된다 — 단, 구 디렉토리가 다른 저장소의
  기록으로 보이면(라운드 기록의 워크트리 origin 불일치) 건드리지 않고 경고만 한다.
  조회·감시는 이전을 일으키지 않는다(무변경 해석이 기본값이다).
- 별도 포인터 파일을 두면 어긋날 수 있는 두 번째 진실이 생기고, eval·실험 런이 진짜 작업
  포인터를 덮는 사고가 난다 — 실제로 났다(`last.json`, design.md 세션 분리 절 참고).
- ABORTED 본문에 저장소 원격 URL·원본 브랜치명을 권장하는 이유: cross-host 동일
  owner/repo(#10) 같은 잔여가 있고, 안내에 표시되는 본문으로 어느 작업의 중단인지 즉시
  식별된다.
- 산출물을 저장소 밖에 두는 이유: 저장소 안에 쌓으면 `git status` 가 흔들리고 PR 에 섞인다.
  `--out` 을 eval 용 별도 경로로 갈라 둔 이유도 같은 계열이다 — `resume.py` 가 찾지 않아
  실험이 진행을 오염시키지 않는다.
- ABORTED 를 산문(decisions.md)이 아니라 마커 파일로 판정하는 이유: 절 이름 파싱은
  `## 중단 근거` 오인, fence 안 예시 오인 같은 엣지 케이스가 끝없이 나와 버렸다. 산문을
  판정 입력으로 삼지 않는 것이 이 설계의 불변식이다.

## P2 자동 반영을 폐지한 실측

초기 설계는 P2 를 자동 반영하려 했다. eval iteration 1 에서 실측한 결과 P2 는 18건 중

남는다. 남는 쪽이 비싸므로 자동 반영은 하지 않는다.

## fix 문장이 다음 라운드의 findings 가 된 3연속 실측 — B2C-53709 (PR #915)

한 티켓의 코드 게이트 7라운드에서 **fix 문장이 원인인 결함이 세 번** 나왔다. 셋 다 리뷰어가
찾은 코드 결함이 아니라 **스킬을 돌린 쪽이 쓴 fix 를 작성자가 그대로 반영한 결과**다.
반영은 매번 정확했다 — 문장이 시킨 대로 했고, 문장이 틀렸다.

**세 번 다 같은 국면에서 나왔다: fix 가 "이미 있는 것" 을 가리킨 순간.**

### 1. 비대칭 방어를 대칭으로 맞추는 fix — `code-1` #7

결함은 *"재발송 중에 확인 버튼이 눌린다"* 였고, 버튼은 `disabled` 로 막는데 **엔터 제출은
`onSubmit` 을 지나 버튼을 우회**하는 구조였다. fix 를 *"`disabled` 조건에 `isSending` 을
추가하고, `onSubmit` 에서도 **같은 조건으로** 방어한다"* 로 썼다.

버튼의 조건은 여섯이었고 작성자가 재구성한 `onSubmit` 가드에서 `otpNum.length < 6` 하나가
빠졌다. `tsc` 0 · ESLint 0 · 테스트 통과. **네 라운드 뒤 외부 보안 리뷰어가 잡았고 그 사이
이 스킬의 라운드는 못 봤다** — 두 목록을 대조하는 리뷰어 지시가 없었기 때문이다.

증상: 1~5자리를 넣고 엔터를 치면 불완전한 번호가 서버로 나가고, `onMutate` 가 직전 실패
안내까지 지워 사용자가 봐야 할 문구가 사라졌다.

### 2. 같은 이름의 컨트롤을 한 묶음으로 부른 fix — `code-5` #2

결함은 *"발송 중 이탈하면 폐기된 challenge 의 문자가 뒤늦게 나간다"* 였다. 재시작 컨트롤이
일반 화면과 pre-auth 만료 화면에 하나씩 있었고, fix 를 *"어느 쪽이든 **두 재시작 컨트롤에
같이** 적용해야 한다"*(= `disabled` 에 `isSending` 추가)로 쓰면서 근거를 *"발송은 보통
1초 안에 끝나므로 이탈이 막히는 시간이 짧다"* 로 댔다.

**두 버튼은 이름만 같았다.** 일반 화면 쪽은 확인·재발송과 함께 있는 보조 경로였고, 만료 화면
쪽은 **그 화면의 전부**였다. 그리고 근거였던 "1초 안에 끝난다" 가 **만료 화면에서는 성립하지
않는다** — 그 화면에 도달했다는 것 자체가 발송이 매달린 채 15분이 흘렀을 수 있다는 뜻이다.

증상: 발송이 응답 없이 pending 인 채 15분이 지나면 유일한 출구가 잠겨 갇힌다(axios 에
timeout 도 없어 상한이 없었다). 다음 라운드에서 **네 축 전원**이 짚었다.

### 3. 새 실패 모드를 기존 분류로 흘려보낸 fix — `code-6` (b)

2번의 회귀를 고치면서 *"응답 없는 요청이 잠금 플래그를 영구 고정한다"* 를 함께 지적하고,
fix 로 axios 인스턴스에 `timeout` 도입을 권했다. 근거는 *"타임아웃이 걸리면 **기존 실패
경로**(`send_failed` · `submit_failed` · 로그아웃 재시도 안내)가 그대로 받아 새 문구를 만들
필요가 없다"* 였다.

**그 경로들은 전부 "확정 실패" 를 전제로 만들어져 있었다** — `send_failed` 는 "보내지
못했다", `no_phone` 은 "번호가 없다", 둘 다 서버가 답을 준 실패다. 타임아웃은 **답이 없는
것**이라 성질이 다르다. 게다가 BFF Route Handler 의 upstream `fetch` 에는 상한도 취소 신호도
없어서 **브라우저가 끊어도 서버는 계속 처리한다.**

증상: 문자는 발송됐는데 화면은 "보내지 못했다"를 띄우고, `setOtpIssuedAtMs` 에 도달하지 못해
`hasIssued=false` 로 남아 **사용자가 손에 든 유효한 번호를 입력조차 못 했다.** 재발송하면
두 통. 구글 로그인 타임아웃은 "권한이 있는 계정인지 확인한다"로 오안내됐다 — 같은 PR 에서
`LoginContractError` 를 세워 계약 위반을 권한 실패와 갈라 놓은 것과 **정확히 같은 성질의
문제인데 그때는 갈랐고 이번엔 안 갈랐다.** 다음 라운드에서 **네 축 전원**이 짚었다.

### 왜 기존 P2 체크리스트로는 안 걸리나

P2 체크리스트의 *"고칠 코드가 주변 코드에서 유일하게 결정되는가 (같은 파일이 이미 쓰는 값,
이미 노출된 함수)"* 는 **재사용을 권장하는 문장**이라 오히려 이 함정 쪽으로 민다. 그 항목이
검사하는 것은 **fix 가 유일하게 결정되는가**이지 **재사용 대상의 전제가 새 입력에도
맞는가**가 아니다. 세 번 다 "유일하게 결정된다" 는 참이었다.

또한 세 fix 는 P2·P1 양쪽에 흩어져 있었다(1번은 P2, 2·3번은 P1 급 갈래 제시). **심각도와
무관한 실수**라 P2 체크리스트 안이 아니라 fix 를 쓰는 모든 자리에 걸리는 규칙이어야 했다.

### 이 실수의 비용과 탐지 경로

세 번 다 **즉시 드러나지 않았다** — 작성자는 문장대로 반영했고 `tsc`·ESLint·테스트·빌드가
모두 통과했다. 셋 다 **다음 라운드의 리뷰어가 찾았고**(뒤 둘은 네 축 전원, 완전히 같은 하나를
짚었다) 각각 라운드를 하나씩 더 쓰게 했다.

부수 관찰: **축을 나눠 돌리는 것이 리뷰 대상 코드뿐 아니라 리뷰 자신의 산출물도 검사한다.**
다만 그 검사에 라운드가 든다 — 쓰는 시점에 거르는 편이 싸다.

7라운드에서는 fix 를 쓰지 않고 **갈래 셋과 각각의 비용만 적어 판단을 넘겼다.** 선택을 가르는
값(이 축의 실제 지연 분포 — 알림톡 발송, house 의 id_token 검증 6항 + nonce 소비 + 자격 조회)을
리뷰하는 쪽이 잴 수 없었기 때문이다. 표본 1회라 규칙이라기보다 **선택지로 열어 둔 것**이다.

## same-origin P1 경고의 출처 — B2C-52951

plan-13~17 P1 전원이 단일 파일 출처였는데 아무도 그 신호를 읽지 않아 17라운드가 났다.

파일로 흩어지는 반복은 기계가 판정하지 않으므로 findings 를 읽는 사람이 같은 신호로

## 미결을 diff 안 문서로 옮기면 — #1003 실측

## 세션 분리가 권장 기본인 이유 — 비용 실측

74세션, $495 API 환산 실측에서 비용의 64% 는 리뷰어가 아니라 **구현·라운드 실행·findings

구현만 한다.

## 마켓플레이스 재업로드 금지의 이유

레지스트리류는 보통 아이템 정체성이 이름 하나뿐이고 소유권 검사·버전·fork 개념이 없어서,
같은 이름으로 올리면 서로의 변경이 조용히 사라진다(설치 디렉토리를 통째로 지우고 다시
쓰는 구현이 흔하다). 설치본 직접 수정도 같다 — 다음 업데이트에 경고 없이 지워진다.

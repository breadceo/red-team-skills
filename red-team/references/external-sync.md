# 게이트 GO 후 — 외부 산출물 최신화 (티켓·이슈)

> SKILL.md 의 「참고 문서」에서 참조된다. **작업 A·B 는 게이트가 GO 로 통과했고
> context.md 에 `## 티켓` 절이 채워져 있을 때만 읽는다** — 절이 없거나 비어 있으면 그 둘을
> 조용히 건너뛴다(경고도 띄우지 않는다. 티켓 없이 도는 라운드가 정상 케이스다).
> **작업 C(인계 코멘트)는 티켓이 없어도 돈다** — 트리거가 게이트 GO 가 아니라 pr-triage
> 9절의 사람 신호이고, 게시 대상이 티켓이 아니라 PR 이다.

**게이트를 통과한 순간이 곧 밖에 있는 산출물이 낡는 순간이다.** 계획 게이트를 도는 동안
계획은 계속 고쳐지는데, 이 작업을 시작하게 만든 Jira 티켓 / GitHub issue 본문은 처음 쓴
내용 그대로다 — 구현이 끝나면 티켓만 읽는 사람(QA·기획·다음 세션)은 틀린 계획을 읽는다.
코드 게이트를 GO 로 통과해도 "무슨 AC 를 무엇으로 충족했는지"는 `~/.red-team/runs2/` 안에만
있다. 그래서 게이트를 통과한 시점에 최신화 초안을 만들어 사용자 승인을 받고 게시한다.

**트리거** — `verdict: GO` + `coverage` 가 partial 이 아님 + `round.json` 의
`access_errors`·`verdict_dissent` 가 비어 있음 + `decisions.md` 의 `보류` 가 비어 있음. `resume.py` 가
"다음 게이트로 가라"고 알려주는 그 시점이다. 파일접근오류가 남은 GO 는 신뢰 불가라
외부에 게시하지 않는다 — 해당 축을 `--merge-into` 로 재실행해 오류를 지운 뒤가 트리거다.

**티켓 종류는 키 형태로 가른다** — `XXX-123` → Jira (Atlassian MCP:
`getJiraIssue` / `editJiraIssue` / `addCommentToJiraIssue`), `owner/repo#N` 또는 이슈 URL →
GitHub (`gh issue view/edit/comment`). 둘 다 적혀 있으면 둘 다 갱신한다. **GitHub 명령에는
전부 `-R <owner/repo>` 를 붙인다** — 생략하면 현재 워크트리 저장소로 폴백돼 다른 저장소의
동명 이슈를 읽고 덮어쓴다(식별자의 저장소 한정자가 명령에서 사라지는 지점이다). 수행
주체는 이 스킬을 따르는 메인 세션이다 — 스크립트가 아니다 (Atlassian MCP 는 대화형
인증이라 스크립트에서 쓸 수 없고, `gh` 는 pr-triage 가 이미 요구하는 의존이라 추가
의존이 없다).

## 계획 게이트 GO — 티켓/이슈 본문을 최신화한다 (작업 A)

마커 구역을 덧붙이는 게 아니라 **본문이 확정된 계획과 어긋난 부분을 실제로 고친다.**
근거는 context.md 의 `## 이 변경이 하려는 것`·`## 스코프 밖`·`## 판정 기준`, 그리고
계획 게이트 라운드들의 `decisions.md` 의 `반영` / `후속 티켓` 이다. `## 계획 전문` 이
있으면 함께 근거로 쓴다 — 없으면 `## 리뷰 대상` 이 가리키는 계획 파일을 읽어 대조한다.
요약 절만 보면 구현 순서류의 변경이 티켓 본문에 낡은 채 남는다.

1. 현재 본문을 읽는다 (`gh issue view <n> -R <owner/repo> --json body` / `getJiraIssue`).
2. 현재 본문 ↔ 확정된 계획을 대조해 **어긋난 문장만** 짚는다. 어긋난 것이 없으면
   "최신화할 것 없음"을 보고하고 끝낸다 — 빈 편집을 게시하지 않는다.
3. 사용자에게 `변경 전 → 변경 후` 를 항목별로 보여주고 승인을 받는다.
4. 승인 시 `gh issue edit <n> -R <owner/repo> --body-file <tmp>` / `editJiraIssue` 로 게시하고,
   무엇을 왜 바꿨는지 **한 줄 코멘트**를 함께 남긴다 (`plan-N GO 반영: <요약>`).

**하지 말 것** — 사람이 쓴 요구사항·배경·수용 조건을 계획 문서 어투로 통째 재작성하지
않는다. 고치는 것은 계획과 실제로 어긋난 부분뿐이다. 후속 티켓으로 분리하기로 한
`pre-existing` 은 본문에 섞지 않는다 — 별도 티켓 후보 보고 경로가 이미 있다(findings 처리 절).

**Jira 본문 write 의 보수 규칙** — `getJiraIssue` 는 markdown 으로 읽으므로 description 의
ADF 미디어(인라인 이미지·첨부)가 변환에서 떨어질 수 있고, 그 본문을 `editJiraIssue` 로
되쓰면 **승인 화면에 드러나지도 않은 채** 미디어가 삭제된다. 변경 전 본문에 이미지·첨부
참조가 보이거나 원형 보존을 확인할 수 없으면 본문 write 를 하지 않는다. 이때 인계하는
것은 **전문 초안이 아니라 항목별 `변경 전 → 변경 후` 패치다** — 읽어온 전문은 이미
미디어가 떨어진 손실본이라, 사람이 그대로 붙이면 결국 같은 유실이 난다. 사람이 Jira UI
에서 문장 단위로 적용해 기존 미디어를 보존한다. `plan-N GO 반영` 코멘트는 **본문 write 가
실제로 성공했을 때만** 남긴다 — write 를 건너뛰고 코멘트만 달면 본문이 낡았는데
최신화됐다는 거짓 이력이 생긴다. 작업 B 의 AC 코멘트는 신규 텍스트라 이 제약이 없다.

## 코드 게이트 GO — AC 체크리스트를 코멘트로 등록한다 (작업 B)

본문은 건드리지 않는다. 티켓/이슈에 **코멘트로** AC 체크리스트를 등록한다. 항목별로:

- AC 문장 — 출처: context.md 의 `## 판정 기준 (Spec AC · Gherkin)`
- 그것을 충족시킨 근거 — 코드 위치 / 커밋 / 테스트 (출처: `## 검증 상태`,
  `decisions.md` 의 `반영`)
- 코드 게이트에서 나왔지만 **후속 티켓으로 뺀 항목**은 별도 하위 목록으로 명시
  (`decisions.md` 의 `후속 티켓`)
- 라운드 식별자(`<repo>/<branch>/code-N`)를 한 줄 남겨 근거 추적이 끊기지 않게 한다

근거 수집은 최종 GO 라운드만 보지 않는다 — **GO 까지의 브랜치 `code-N` 라운드 전부**의
`decisions.md` 를 순회해 `반영`·`후속 티켓` 을 모으고 중복을 걷어낸다. 마지막 라운드는
findings 0 으로 GO 라 `decisions.md` 가 비어 있는 게 보통이고, 수정 커밋·후속 티켓의
근거는 그 앞 라운드들에 있다.

**멱등성** — 같은 라운드로 두 번 등록하지 않는다. 코멘트 첫 줄에 `red-team AC: code-N`
식별자를 두고, 게시 전 기존 코멘트를 훑어 같은 식별자가 있으면 새로 달지 않고
**그 코멘트를 수정한다** (pr-triage 의 keep-first 앵커와 같은 취지다). 수정 대상 판정은
첫 줄 앵커만으로 하지 않는다 — **본문의 전체 라운드 식별자(`<repo>/<branch>/code-N`)까지
일치할 때만** 수정한다. 같은 티켓을 여러 브랜치가 공유하면 `code-N` 번호가 겹칠 수 있고,
앵커만 보면 다른 브랜치의 근거를 덮어쓴다. 수정의 실행 수단: 코멘트 전수 조회 때 숫자
ID 를 보존하고 `gh api -X PATCH repos/<owner>/<repo>/issues/comments/<id> -F body=@<tmp>`
로 고친다 — 승인된 수정 전문을 `body` 로 넘긴다(payload 없이 보내면 GitHub 필수 필드
검증에서 실패한다). `gh issue comment` 는 임의 코멘트를 수정하지 못한다(`--edit-last` 는
마지막 자기 코멘트만 대상이다). Jira 도 같은 멱등성이다 —
앵커 조회로 기존 코멘트의 ID 를 확보하고, MCP 가 코멘트 수정을 지원하면 그 ID 로
수정한다. 수정 경로가 없으면 **중복 등록하지 않는다** — 기존 앵커가 낡았다는 사실과 새
내용을 사용자에게 보고하고 수동 인계한다. **같은 라운드를 두 세션에서 동시에 처리하지
않는다** — 그래도 재조회 창 사이로 중복이 생겨 앵커 조회에서 같은 식별자 코멘트가 둘 이상
발견되면, 첫 코멘트를 진실로 삼아 수정하고(keep-first — pr-triage 앵커와 같은 원칙) 중복
사실을 사용자에게 보고한다. 원자적 방지는 위 경합 창과 같은 이유로 불가능하다 —
결정론적 사후 정리가 계약이다.

**pr-triage 흐름 안에서 트리거됐다면 순서가 하나 더 있다** — 그쪽 6-1(처리 결과 기록)을
마친 뒤에 초안을 만든다. 기록 전에 만들면 방금 고친 수정의 커밋·근거가 `decisions.md` 에
아직 없어 AC 코멘트에서 빠지고, 같은 라운드에 다시 갱신할 트리거가 없다.

`## 판정 기준` 이 비어 있으면(Spec AC 가 없는 작업) 코멘트를 만들지 않고 그 사실만
보고한다. 승인 게이트는 계획 게이트와 동일하다 — 코멘트 전문을 보여주고 승인 후 게시한다.

## approve·LGTM 후 — 인계 코멘트를 PR 에 남긴다 (작업 C)

**게이트 기록은 `~/.red-team/runs2/` 에만 있다.** 다른 기기·새 워크트리·다른 사람의
세션은 그 디렉토리를 읽지 못한다. 그래서 pr-triage 는 `의사결정 기록: 없음` 인 PR 을
위해 3·4절을 건너뛰고 코드로만 판정하는 열화 경로를 따로 두고 있다(그쪽 「의사결정 기록이
없는 PR」). 작업 C 는 그 기록을 PR 코멘트로 내보내 **열화 경로를 정상 경로로 되돌린다** —
새로 쓰는 문서가 아니라 이미 있는 기록의 렌더다.

**그 복귀는 실제로 소비된다.** pr-triage 의 `fetch_comments.py` 는 로컬 라운드가 없을 때
이미 받아온 코멘트 페이로드에서 아래 앵커를 찾아 `record` 를 채우고
(`{"source": "handoff-comment", …}`), `의사결정 기록: red-team 인계 코멘트 #N` 으로 출력하며
`--show-scope` 도 그 본문에서 절을 뽑는다(그쪽 `references/edge-cases.md` 「인계 코멘트
폴백」). 로컬 기록이 있으면 로컬이 이긴다 — 폴백이지 대체가 아니다.

**그래서 앵커와 절 이름이 계약이다.** 앵커는 코드펜스·blockquote 밖의 제 줄에 그대로 두고
(인용된 앵커는 파싱에서 제외된다), 렌더에서 `## 스코프 밖`·`## 후속 티켓` 의 절 이름을
바꾸거나 풀어쓰지 않는다 — 바꾸면 `--show-scope` 가 조용히 빈손이 된다.

**트리거는 pr-triage 9절과 같은 사람 신호다** — `<APPROVED>`·사람 리뷰어의 승인 문구,
또는 사용자의 직접 지시. 그쪽 본문 최신화 승인이 끝난 뒤에 **인계 코멘트도 남길지 묻는다.**
자동 발동 금지. 미처리 코멘트가 남아 있으면 그것부터다.

**게이트 GO 직후를 트리거로 쓰지 않는다** — 트리아지 라운드가 계속 돌며 코드가 바뀌므로
그 시점의 인계는 즉시 낡는다. approve 는 코드가 멈춘 첫 지점이다. 그래도 이후에 커밋이
붙으면 아래 앵커로 **재생성**한다(덧붙이지 않는다).

**게시 위치는 PR 코멘트다 — 티켓이 아니다.** 이어받는 대상이 브랜치이고, 같은 티켓을
여러 브랜치가 공유하면 앵커가 겹쳐 남의 인계를 덮는다(작업 B 의 그 함정과 같다).
`red-team` 을 안 거친 PR(`context.md` 부재)이면 렌더할 기록이 없으므로 이 단계 전체를
조용히 건너뛴다.

### 무엇을 담나

브랜치의 **전 라운드**를 순회해 모은다 — 마지막 GO 라운드만 보면 근거가 앞 라운드에 남는다.

| 담을 것 | 원천 |
|---|---|
| 무엇을 하려는 변경인가 · 티켓·PR·브랜치 | `## 이 변경이 하려는 것` · `## 티켓` · `## 리뷰 대상` |
| 다시 제안하지 말 것 | `### 기각한 대안` · `decisions.md` 의 `## 철회한 주장` |
| 깨면 안 되는 축 | `### 불변식` |
| 되물으면 안 되는 확정 사항 | `### 기획·정책 확인 완료 사항` |
| 남은 것 · 후속 티켓 | `## 스코프 밖` · `decisions.md` 의 `## 후속 티켓` |
| 검증을 어떻게 돌리나 | `## 검증 상태` |

**가장 값이 큰 것은 "다시 하지 말 것" 이다.** 이어받는 사람이 재조사로 잃는 시간은
대부분 이미 기각된 길을 다시 걷는 데 쓰인다. 반영 목록만 나열한 인계는 커밋 로그와
중복이라 값이 없다.

**담지 않을 것** — 자격증명·토큰, 로컬 절대경로, 개인 기기·계정 식별자. 대상 저장소에
실행 절차 문서가 있으면 **경로를 인용하고 내용을 복사하지 않는다**(복사본이 낡는다).
`## 판정 기준` 이 비어 있어도 이 단계는 돈다 — AC 없이도 기각한 대안·불변식에 값이 있다.

**작업 B 와 겹치지 않는다** — B 는 "무슨 AC 를 무엇으로 충족했나"(리뷰어·QA 가 읽는다),
C 는 "재조사 없이 이어받을 것"(다음 세션이 읽는다). 후속 티켓은 양쪽 원천이 같으니
C 에서 재서술하지 말고 **B 코멘트를 링크한다.**

### 절차

1. 초안을 만든다. 본문 첫 줄은 앵커 `red-team handoff: <repo>/<branch>` —
   **라운드 번호를 넣지 않는다**(브랜치 생애 전체에 하나이고, 번호를 넣으면 라운드마다
   새 코멘트가 쌓인다). 붙여넣기 대상이므로 프롬프트 본체는 접은 블록(`<details>`) 안의
   코드 펜스에 둔다.
2. 기존 코멘트를 훑어 같은 앵커가 있으면 **새로 달지 않고 그 코멘트를 수정한다** —
   `gh api -X PATCH repos/<owner>/<repo>/issues/comments/<id> -F body=@<tmp>`. 앵커가 둘
   이상이면 keep-first 로 첫 것을 진실로 삼고 중복 사실을 보고한다(작업 B 와 같은 규약).
3. `변경 전 → 변경 후` 로 승인받고 게시한다 — 새 코멘트든 수정이든 같다.

## 공통 규칙

- **승인 없이 write 하지 않는다.** 승인 요청은 한 번에 하나의 산출물만 다룬다.
  자동 게시는 옵션으로도 만들지 않는다.
- **읽기 → 대조 → 변경 없음이면 조용히 종료.** 빈 편집·중복 코멘트를 만들지 않는다.
- **대조는 부재 검사가 아니라 어긋남 검사다.** 수집한 항목이 본문에 없을 때 더하는 것으로
  끝나지 않는다 — 본문의 기존 서술과 상충하면 그 문장을 고친다. 안 고치면 모순된 두 서술이
  공존한 채 게시된다. 그리고 **승인은 항상 `변경 전 → 변경 후` 다** — 새 write 든 기존
  코멘트 수정이든 같다. 수정이면 기존 내용 → 수정 초안을 항목별로 보여준 뒤 승인받는다.
  새 전문만 보여주면 무엇이 지워지는지 모른 채 승인하게 된다.
- **실패는 게이트를 막지 않는다 — 단 read 실패와 write 실패는 처리가 다르다.**
  write 실패(`gh` 인증 실패 / MCP 미연결 / 권한 없음)면 그 사실과 게시하려던 초안 전문을
  출력해 **사용자가 손으로 붙일 수 있게** 한 뒤 계속 진행한다. **최초 read 가 실패하면
  초안 자체를 만들 수 없다** — 현재 본문을 추측해 채우지 말고, 반영하려던 변경 목록
  (항목별 요지)만 출력하고 계속 진행한다. 어느 쪽이든 외부 읽기·쓰기 실패로 GO 가
  취소되지는 않는다.
- **게시 직전 재확인은 대상만이 아니라 초안의 입력 전부다.** 승인을 기다리는 동안 남이
  그 본문을 고칠 수 있다 — 초안의 원본과 달라졌으면 게시하지 않고 재대조해 새 초안으로
  다시 승인받는다. 근거로 쓴 입력(계획·decisions.md·검증 상태)이 초안 생성 이후
  달라졌어도 같다 — 다른 세션이 새 라운드를 만들었으면 대상 본문이 그대로여도 초안은
  낡은 것이다. 폐기하고 최신 입력으로 재작성해 다시 승인받는다.
  작업 B 의 앵커도 같다: 게시 직전 다시 조회해 그 사이 같은 식별자의 코멘트가 생겼으면
  새로 달지 않고 수정으로 전환한다. `--body-file` 통째 덮어쓰기가 남의 수정을 유실시키는
  사고 지점이 정확히 여기다. **재조회와 write 사이의 초 단위 경합 창은 남는다** —
  GitHub API 에는 본문 CAS(조건부 갱신)가 없어 문서 프로토콜로는 닫을 수 없는 매체의
  한계다. 이 잔여 창은 수용한다: write 는 사람이 승인한 초안이고, 사고가 나면 GitHub
  편집 이력으로 복구한다. 잠금·조정 절차를 새로 만들지 않는다.

pr-triage 의 approve·LGTM 후 PR 본문 최신화(그쪽 9절)도 같은 공통 규칙을 따른다 — 넷이 한 벌이다.

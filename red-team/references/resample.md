# core 축 재샘플링 — GO 후보 라운드에서 한 번 더 돌린다

> SKILL.md 「루프」절에서 **라운드가 GO 로 나왔을 때** 읽는다. MoE 와 무관하다 — 옵트인
> MoE(`references/moe.md`)를 끈 기본 경로(전체 축)에서도 적용한다. 실측 근거는
> `references/design.md` 의 6라운드 재현 절이다.

## 왜

`a-code` 는 매 런 서로 다른 실제 결함을 지목한다 — 불안정이 아니라 탐색 폭이다
(`references/design.md`). 이 규칙의 근거는 그 해석의 **뒷면**이다: **탐색 폭이 넓다는
것은 한 번의 GO 가 커버리지를 보장하지 않는다는 뜻이다.** 축이 결함을 "찾을 수 있다" 와
"이번 런에서 찾았다" 는 다르다. 같은 diff·같은 컨텍스트로 6라운드를 돌렸을 때 원본의
`GO / findings 0` 은 **2번만** 재현됐다.

## 규칙

라운드가 GO 로 나왔으면 **확정 전에 core 축을 한 번 더 돌려 원 라운드에 병합한다.**
샘플 수 N 의 기본은 2(원 라운드 + 재샘플 1회). 새 배선이 아니라 호출 시점 규칙이다.

```bash
python3 "<red-team-skill>/scripts/run_round.py" \
  --cwd "<저장소 경로>" --gate code \
  --merge-into "<GO 후보 라운드 디렉토리>" --reviewers a-code
```

- **병합 후의 verdict 만 판정이다.** 재샘플이 `regression` 을 내면 **NO-GO 로 돌아가는
  것이 정상** — 고치고 다음 라운드로 간다. 그 라운드가 다시 GO 면 거기서 또 재샘플한다.
- `regression` 0 이면 GO 확정. N>2 를 쓰려면 GO 가 유지되는 동안 같은 명령을 반복한다.
- core 축은 `run_round.py` GATES 의 `core` 플래그로 정의된다 — 코드 게이트는 `a-code`,
  계획 게이트는 `a-plan`. 게이트에 맞는 축 이름을 넘긴다(`--gate plan` 이면 `a-plan`).
- 재샘플은 그 라운드의 `context.md` 로 돈다(`--merge-into` 는 `--context` 를 받지 않는다).
  즉 **컨텍스트를 고정한 채 축만 다시 뽑는 것**이고, 그게 이 규칙이 재는 것이다.

## 자동 필수가 아니다 — 비용과 건너뛰는 자리

core 축 1회는 라운드 비용의 20~30%(`report_usage` 집계)이므로 **GO 라운드당 +25%
수준**이다. 라운드 수에 비례하지는 않는다 — GO 후보는 티켓당 보통 1~2회다. 그래도 라운드
비용을 무조건 늘리는 장치는 아니다. 아래 중 하나라도 맞으면 건너뛰고 **건너뛴 사실과
사유를 `decisions.md` 에 한 줄 적는다**(적지 않으면 다음 세션이 재샘플했다고 오해한다):

- diff 가 한 파일·한 함수 규모다 — 탐색 폭이 좁아 재샘플이 같은 곳을 다시 본다
- 이 브랜치에서 이미 재샘플로 GO 를 확정했고 그 뒤 코드가 아니라 **컨텍스트만** 바뀌었다
- 계획 게이트에서 2라운드 이상 P1 이 0 이다 — 계획 게이트는 2축뿐이라 재샘플 1회의 비용
  비중이 코드 게이트보다 크고, 재는 대상(순서·전제)이 코드보다 좁다

## 왜 GO 라운드에만 — NO-GO 에는 걸지 않는다

두 가지 이유고, 두 번째가 결정적이다.

1. NO-GO 라운드는 **다음 라운드가 같은 축을 다시 돌린다** — 재샘플이 공짜로 일어난다.
   재샘플이 값을 하는 자리는 "이 라운드로 끝낸다" 는 판정 직전 한 곳뿐이다.
2. **GO 라운드에서만 병합이 곧 합집합이다.** `--merge-into` 는 그 축의 이전 산출물을
   `<축>.superseded-<stamp>.*` 로 밀어내고 **덮는다** — round.json 에 남는 것은 새
   샘플뿐이다. GO 후보의 `regression` findings 는 정의상 0 이므로 `0 ∪ 새 샘플 = 새
   샘플`, 즉 병합 결과가 그대로 합집합이다. NO-GO 라운드에 같은 명령을 쓰면 이전 샘플의
   findings 가 round.json 에서 사라진다 — 그러면 합집합을 손으로 만들어야 하고 그 배선은
   없다(`run_round.py` 에 플래그를 늘리지 않는다).

**GO 라운드에도 한 가지 유실은 있다.** GO 를 막지 않는 findings(`pre-existing` ·
`out-of-scope`)는 덮이면서 round.json 에서 사라진다. 그래서 재샘플 **전에** 그 별도 티켓
후보 요약을 `decisions.md` 의 `## 후속 티켓` 으로 먼저 옮긴다. 옮기기 전에 덮었으면
`<축>.superseded-<stamp>.json` 에 그대로 있다 — 그 파일을 읽는다.

## 합집합의 중복 처리

같은 결함을 두 샘플이 다르게 서술하면 **사람은 한 번만 판정한다.**

- **같은 파일 · 같은 술어**(같은 심볼이나 줄 앵커에 대한 같은 주장)를 지목한 findings 는
  **한 건으로 올리고 두 서술을 함께 보여준다.** `classification` 이나 `severity` 가
  갈리면 **더 엄한 쪽**을 취한다(`regression` > `pre-existing`, P1 > P2) — 사람이 더
  자세히 보는 쪽으로 기울이는 것이 안전하다.
- **같은 결함인지 확실하지 않으면 따로 올린다.** 비대칭이다 — 잘못 묶으면 한 건이 무음으로
  유실되고, 잘못 나누면 사람이 "중복이다" 한마디로 닫는다.
- 이 규칙이 실제로 걸리는 자리는 좁다. GO 라운드에만 걸고 재샘플이 결함을 내는 순간 그
  라운드가 NO-GO 로 끝나므로, 한 라운드 안에서 두 샘플이 **동시에** `regression` 을 내는
  경우는 생기지 않는다. 겹치는 것은 위의 `pre-existing` 티켓 후보 요약뿐이다.
